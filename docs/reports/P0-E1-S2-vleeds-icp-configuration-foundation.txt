1. SUMMARY
--------------------------------------------------------------------------------
A workspace can now define who it wants to sell to, entirely as data:
  - its business profile is editable (name, primary domain, website, description)
  - a new workspace-owned table public.icp_profiles stores ideal-customer
    criteria, target geographies, decision-maker titles, buying signals,
    exclusion signals and a scoring model as versioned, validated jsonb
  - several profiles per workspace are supported by the schema; at most one
    active default is enforced by the database; Settings edits the default
  - six Settings rows are now live, each opening a sheet editor (right-side on
    desktop, near-full-height bottom sheet on phones). Owners and admins edit;
    members get the same sheets read-only. Status pills are computed from
    saved data (Not configured / Partially configured / Configured /
    No exclusions)
  - enforcement is layered: RLS + column grants + CHECK constraints in the
    database, then authentication, workspace re-authorization, role check and
    Zod validation in every server action, then the same Zod schemas in the
    browser for instant feedback
  - 41 new adversarial RLS tests, 41 new unit tests, 66 new browser checks;
    `npm.cmd run verify` passes; the S1A browser review still passes 50/50

Not built, by design: discovery, Google Places/Apollo/any provider, enrichment,
calling, campaigns, lead records, scoring of real companies, AI suggestions,
multi-profile management UI.

5. ICP_PROFILES STRUCTURE
--------------------------------------------------------------------------------
id uuid pk · workspace_id uuid → workspaces ON DELETE CASCADE (immutable)
name text 1–120 · description text ≤2000 (the ideal-customer description)
is_default bool · archived_at timestamptz
schema_version int CHECK IN (1) · revision int ≥1 (server-managed)
ideal_customer jsonb · target_geographies jsonb · decision_maker_titles jsonb
buying_signals jsonb · exclusion_signals jsonb · scoring_model jsonb
created_by uuid default auth.uid() (immutable) · created_at · updated_at
UNIQUE (workspace_id, id) for future composite FKs (campaigns, lead_scores)

CHECK constraints
  - schema_version in (1)
  - NOT (is_default AND archived_at IS NOT NULL)
  - ideal_customer: object, ≤32 KB, minEmployees ≥ 0, minEmployees ≤ maxEmployees
  - target_geographies: array, ≤100 items, ≤64 KB
  - decision_maker_titles / buying_signals / exclusion_signals: array, ≤50, size-capped
  - scoring_model: object, ≤8 KB, thresholds.a and thresholds.b numeric with
    1 ≤ b < a ≤ 100 (missing/non-numeric thresholds rejected)

Revision: +1 by trigger when any configuration column changes; unchanged
otherwise. Not granted to API roles. Saves are optimistic: the update is
filtered by the revision the editor opened with; a mismatch returns "someone
else changed this configuration" instead of overwriting. No history table or
event sourcing: campaign-time immutable snapshots (or pinned revisions) will
be introduced with campaigns, and lead scores will record profile id + revision.

Deviations from the suggested shape (deliberate):
  D-S1 Section columns are NULLABLE with no default. NULL = never saved; an
       empty array saved on purpose is meaningful ("No exclusions"). Defaults
       of '{}'/'[]' would make "never configured" indistinguishable.
  D-S2 No set-default function. The partial unique index blocks a second
       default; switching is "clear old, set new" in one transaction (tested).
       No UI needs it yet, so no function was added.
  D-S3 jsonb keys are camelCase (countryCode, minEmployees…), matching the
       spec's geography example; category-weight keys use the spec's
       snake_case identifiers (company_fit, …).
  D-S4 New helper private.has_workspace_role (the data-model plan named it);
       needed for owner/admin writes on a workspace-keyed table.
  D-S5 B threshold ≥ 1 (and therefore A ≥ 2): with B = 0 the C range would be
       empty, which the spec calls incoherent.
  D-S6 Every geography requires a country (ISO code). A bare "region" with no
       country is ambiguous across countries; requiring the country avoids
       any single-country assumption.

6. VALIDATION SCHEMAS (src/lib/config/icp.ts, schema_version 1)
--------------------------------------------------------------------------------
Common: text is trimmed with internal whitespace collapsed; optional text ""→null;
objects are strict (unknown keys rejected) except geography items, whose derived
fields are stripped and recomputed; duplicate checks are case-insensitive on
normalized text; entry ids must be UUIDs and unique within their list.

idealCustomerSectionSchema  { name 1–120, description ≤2000|null, idealCustomer }
  idealCustomer  { industries[≤30], companySize{minEmployees,maxEmployees},
                   characteristics[≤30], keywords[≤30], notes ≤2000|null }
  tags 1–80 chars, no duplicates; employees: whole numbers 0–10,000,000 or
  null; min ≤ max
geographiesSchema [≤100] { id, countryCode (ISO alpha-2, case-insensitive in),
                   region ≤120|null, city ≤120|null, label ≤120|null }
                   → stored with countryName (server-derived); duplicate
                   (country, region, city) targets rejected
decisionMakersSchema [≤50] { id, title 1–120, priority primary|secondary|fallback,
                   seniority executive|director|manager|individual_contributor|null }
buyingSignalsSchema [≤50] { id, name 1–80, description ≤500|null,
                   weight integer 1–100, enabled }
exclusionSignalsSchema [≤50] { id, name, description, behavior
                   hard_exclude|penalty, penalty, enabled }; penalty required
                   (1–100) for penalty, must be null for hard_exclude
scoringModelSchema { thresholds{a,b}, categoryWeights{company_fit, geography_fit,
                   decision_maker_fit, buying_signal_fit} }; integers;
                   1 ≤ b < a ≤ 100; weights 0–100 summing to exactly 100
icpSectionInputSchema  discriminated union on `section` with
                   { profileId uuid|null, revision int≥1|null, value }
businessProfileSchema { name 1–120, primaryDomain (normalized hostname)|null,
                   websiteUrl http(s)|null, description ≤2000|null }, strict

Stored data is parsed again on read; a section that no longer matches is
treated as unsaved and logged server-side (never shown half-parsed).

7. RLS / ACCESS POLICIES
--------------------------------------------------------------------------------
RLS ENABLED on icp_profiles (catalog test covers every public table).
Privileges: anon nothing. authenticated:
  SELECT (all columns)
  INSERT (workspace_id, name, description, is_default, schema_version,
          ideal_customer, target_geographies, decision_maker_titles,
          buying_signals, exclusion_signals, scoring_model)
  UPDATE (name, description, is_default, archived_at, schema_version,
          + the six jsonb columns)
  → id, created_by, revision, timestamps never writable; workspace_id not
    updatable (and trigger-protected); no DELETE privilege.
Policies (TO authenticated):
  icp_profiles_select_member  SELECT  private.is_workspace_member(workspace_id)
  icp_profiles_insert_admin   INSERT  private.has_workspace_role(workspace_id, {owner,admin})
  icp_profiles_update_admin   UPDATE  same, USING and WITH CHECK
  (no DELETE policy)
Workspaces (unchanged S1 policy): UPDATE by owner/admin — used for business
profile editing.

9. BUSINESS-PROFILE EDITING
--------------------------------------------------------------------------------
Edit (owners/admins) opens the sheet: Workspace name, Primary domain, Website,
Description, with Save / Cancel. Validation runs in the browser and again in
updateBusinessProfile (strict Zod), which writes exactly four columns via
updateWorkspaceProfile; a refused update (zero rows under RLS) is reported as
"Only owners and admins…". On success the action calls refresh(): the card
(and the workspace switcher) update in place, no navigation, and focus returns
to Edit. Errors show inline under the field (aria-describedby) plus a summary
alert. The slug is not changed by a rename. logo_url left out (not needed; no
upload path exists). Concurrency: last write wins (see §23).


--------------------------------------------------------------------------------
10. ICP EDITOR
--------------------------------------------------------------------------------
Profile name (defaults to "Default profile" for a new workspace), ideal-customer
description, industries/categories as removable chips, company size min/max,
company characteristics chips, positive keyword chips, notes. Chips are added
with Enter, comma or the Add button; duplicates are refused immediately; each
chip has a "Remove <kind> <value>" button. The first save of ANY section creates
the workspace's default profile (no SQL or setup needed); the sheet says so.


--------------------------------------------------------------------------------
11. GEOGRAPHIES
--------------------------------------------------------------------------------
Add/edit form: Country (select of all ISO countries, names from Intl), Region
/state/province, City/locality, optional Display label. Saved targets appear as
compact rows with a scope line (Country / Region · <country> / City · <country>)
and labelled Edit / Remove buttons. Editing loads a row into the form ("Update
target"/"Cancel edit"). Duplicate targets are refused. Saving with a half-
filled form asks the user to add or clear it first. No maps, autocomplete or
external API.


--------------------------------------------------------------------------------
12. DECISION MAKERS
--------------------------------------------------------------------------------
"Add role" appends a row and focuses its title. Each row: Title, Priority
(Primary/Secondary/Fallback; first role defaults to Primary), optional
Seniority, Remove. Duplicate titles (trim/space/case-insensitive) are rejected
on the offending row. Read-only view lists titles with a priority pill.


--------------------------------------------------------------------------------
13. BUYING SIGNALS
--------------------------------------------------------------------------------
"Add signal" → name, optional description, weight (1–100, default 50) with a
compact bar beside the number, Enabled switch (role="switch", state also in
text), Remove. No suggestions, no AI.


--------------------------------------------------------------------------------
14. EXCLUSION SIGNALS
--------------------------------------------------------------------------------
"Add exclusion" → name, optional description, "When a company matches":
Exclude (hard exclusion) or Lower score (penalty, points 1–100, default 20),
Enabled switch, Remove. Calm treatment: neutral cards; hard exclusion shown as a
neutral "Excludes" pill with a ban icon in read-only views; no red. Saving an
empty list is allowed and records "No exclusions".


--------------------------------------------------------------------------------
15. SCORING CONFIGURATION
--------------------------------------------------------------------------------
"A grade from" / "B grade from" inputs with a live preview that reflects the
values (e.g. A 80–100 Strongest fit · B 55–79 Reasonable fit · C 0–54 Weaker
fit); incoherent input hides the preview and explains the rule. Category
weights (company, geography, decision-maker, buying signals) with bars and a
running "Total n of 100". An unsaved model is pre-filled with suggestions
(A 75 / B 50; 40/20/20/20) clearly labelled as not saved; the status stays
"Not configured" until Save. No scores are computed anywhere.

16. CONFIGURATION-STATUS RULES (src/lib/config/icp-status.ts)
--------------------------------------------------------------------------------
Only saved data counts; NULL (never saved) is always Not configured.
  Ideal customer   Configured = description AND ≥1 company criterion
                   (industry/characteristic/keyword or a min/max size);
                   Partially configured = only one of the two; else Not configured
  Geographies      Configured = ≥1 target; else Not configured
  Decision makers  Configured = ≥1 title; else Not configured
  Buying signals   Configured = ≥1 ENABLED signal; Partially configured = signals
                   exist but all disabled; else Not configured
  Exclusions       Not configured = never saved; "No exclusions" = saved with
                   none enabled (green, counts as configured); Configured = ≥1
                   enabled exclusion
  Scoring          Configured = a valid model saved; else Not configured
Pill tones: attention (peach) / warning (amber) / brand (green), always with
text. Enrichment providers and Calling provider: "Not configured" + "Available
in a later setup step", not interactive.

21. SECURITY REVIEW
--------------------------------------------------------------------------------
Inspected: new RLS policies, grants, triggers, helper; server actions; DAL;
client components and bundle; error paths.

Verified
  S1  Workspace authorization: every action validates the workspace id as a
      UUID, re-loads it through RLS (findWorkspace) and checks the caller's
      role before writing; RLS re-checks owner/admin on the row. Foreign,
      missing and malformed ids all yield "This workspace is not available."
  S2  Role permissions: members cannot write (tests + action check); admins
      have owner-equivalent configuration rights only.
  S3  Input validation: strict Zod on every server mutation (unknown keys
      rejected), list and length limits, plus DB CHECKs for types, sizes,
      schema version and core bounds. Browser validation is UX only.
  S4  Mass assignment: the DAL writes a fixed column map per section; client
      input is never spread into an insert/update; is_default, archived_at,
      workspace_id, created_by and revision cannot be set from the editors.
  S5  Immutable ownership: workspace_id/created_by protected by trigger and
      missing grants; revision server-managed (tested, incl. as table owner).
  S6  User-supplied ids: workspaceId re-authorized; profileId updates are
      also filtered by workspace_id (a profile id from another workspace
      matches nothing) and by RLS; jsonb entry ids are UUIDs scoped to one
      profile with no authorization meaning.
  S7  Errors: DB error codes are mapped to fixed messages; raw messages are
      only logged server-side; read failures go to the existing generic
      error boundary.
  S8  No privileged credentials: no service-role path added; bundle scan
      clean; the browser made zero requests to Supabase.
  S9  No open redirect: actions accept no navigation targets; the only
      redirect is the fixed "/login".
  S10 Concurrency: optimistic revision check prevents silent overwrite of
      ICP configuration; a racing first save cannot create two defaults.
  S11 SECURITY DEFINER helper pins search_path='' and is not executable by
      anon (existing catalog tests now include it).

Findings / recommendations
  F1 (Low)  Business-profile saves are last-write-wins (workspaces has no
            revision column). Acceptable for 4 descriptive fields.
  F2 (Low)  Per-entry jsonb rules (weights, penalties, duplicates, ISO codes)
            are enforced by Zod, not the database. A client bypassing the app
            with direct API access is still limited to owners/admins of that
            workspace and by the DB size/type/threshold checks. Add DB-side
            JSON validation (e.g. pg_jsonschema) if direct API writes are ever
            allowed.
  F3 (Low)  Carried over: no Content-Security-Policy yet (S1 F1).
  F4 (Info) Member attempts to call the server actions directly were not
            exercised end-to-end in a browser (would need the real stack);
            covered by the action's role check and the RLS tests.
  F5 (Info) website_url still accepts http:// (S1 rule); javascript: and
            other schemes are rejected; links open with noopener noreferrer.
