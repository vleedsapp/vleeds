1. ROOT CAUSE OF READ-ONLY SETTINGS
--------------------------------------------------------------------------------
The cause was NOT role, membership, RLS or server-action authorization. It
was a dev-only client bug in the shared editing sheet
(src/components/settings/config-sheet.tsx).

Diagnosis, in order:
  - DB: pilot@vleeds.test is `owner` of org "Chelly", which owns
    "Chelth Test". The pilot created both through the normal onboarding page.
  - UI: Settings showed "Your role: Owner". The Edit button and all six
    ICP "(edit)" rows were rendered and hydrated.
  - "Not configured" was truthful: Chelth Test had 0 icp_profiles rows.
  - Clicking Edit opened nothing. On the component's fiber, the state DID
    flip to open=true, then went back to false.
  - The same flow on a production build (`next start`) worked.

Mechanism: ConfigSheet opens its native <dialog> in a mount effect
(showModal) and closes it in the cleanup (close()). It also forwards the
dialog's `close` event to onClose. React Strict Mode (development only)
runs mount → cleanup → mount. The cleanup's close() QUEUES a `close`
event. The second mount re-opens the dialog. Then the queued event fires,
onClose runs, and the parent unmounts the sheet in the same instant it
opened. Every sheet built on ConfigSheet was affected in `next dev`:
business profile, all six ICP editors, add-contact, the contact workflow
sheets, the import decision sheet and the fit sheet. Earlier browser reviews ran on
`next start` (production), so this never surfaced before. The pilot is the
first run under `next dev` on the real stack.

5. ROOT CAUSE OF NEXT.JS UNCACHED-DATA WARNING
--------------------------------------------------------------------------------
Next.js 16.4 with cacheComponents validates instant navigation in dev
(validationLevel 'warning' by default). It simulates both the page load
and client navigation into each page segment.

createSupabaseServerClient() calls `await connection()` (and cookies()).
That is correct and stays: the session is per-request, and without it
supabase-js reads the clock during App Shell prerendering. It is reached
from every workspace page (SectionPage → getWorkspace, and the Discover,
Leads and Import pages directly).

The only <Suspense> covering those pages was src/app/w/[workspaceId]/
loading.tsx. For a client navigation between sibling sections (Today →
Settings), the [workspaceId] layout and that boundary are ALREADY MOUNTED,
so it doesn't cover the new page segment. The navigation blocks on
connection(), and dev reported:
  Route "/w/[workspaceId]/<section>": Next.js encountered uncached data
  during prerendering or a navigation.
It affected every workspace section: today, discover, leads, campaigns,
settings and leads/import, not only Settings. (Source:
next/dist/server/app-render/blocking-route-messages.js,
createDynamicBodyErrorInNavigation.)

This was a separate issue from §1. Fixing it alone did not make the sheets
open. Both fixes were needed.

6. EXACT NAVIGATION/CACHE FIX
--------------------------------------------------------------------------------
The [stream] fix from the Next.js docs (instant-navigation guide,
loading.js: "loading.js wraps page.js … in a <Suspense> boundary"):
  each page segment gets its own loading.tsx, which re-exports the existing
  workspace PageSkeleton (no new design).
    src/app/w/[workspaceId]/{today,discover,leads,campaigns,settings}/loading.tsx
    src/app/w/[workspaceId]/leads/import/loading.tsx
    src/app/w/[workspaceId]/leads/import/[batchId]/loading.tsx
Not used:
  - force-dynamic
  - `instant = false`
  - suppressing validation
  - removing connection()
  - any cache directive
Caching behaviour is unchanged. The App Shell now renders immediately on
navigation, and the authenticated content streams in.

Also fixed (found by the new browser check, pre-existing): a hydration
mismatch on Leads. LeadFilters (client) built its country list from the
runtime's Intl.DisplayNames. Chrome's ICU names FK, HK, MO and PS
differently from Node's (e.g. "Hong Kong" vs "Hong Kong SAR China"), so
the server-rendered <option>s failed hydration. The Leads page (server)
now computes countryOptions() once and passes it in. Other countryOptions
users render only after a user action (inside sheets), so they are not
affected.

ConfigSheet fix (§1): onClose fires only when the dialog is still closed
when the queued `close` event arrives.
