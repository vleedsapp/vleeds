1. SUMMARY
--------------------------------------------------------------------------------
Companies can now be evaluated against an ICP: "how well does this company
match, and why?"
  - Evaluate fit (company drawer) → review the profile's buying/exclusion
    signals (Present / Not present / Unknown, optional note) → the server
    evaluates the company's durable data with a pure TypeScript engine.
  - The result shows:
      · fit score 0–100 and A/B/C grade (or Excluded with reasons)
      · data coverage (separate from fit)
      · a category breakdown with configured and effective weights
      · penalties
      · "Why this score?" and "Improve data coverage"
      · the profile + revision, and Current/Outdated
  - A result is current only for the profile's current revision AND the
    current SHA-256 fingerprint of its scoring inputs. Company, contact,
    signal or ICP changes make it Outdated until it is recalculated.
  - Leads shows the default ICP's current grade with its fit ("A 84 fit"),
    or Excluded / Outdated / —. The Grade filter adds Excluded, Outdated
    and Not scored.
No AI, no provider calls, no qualification or suppression changes, no batch
or background scoring.
Quality gate: npm.cmd run verify EXIT 0 (440/440 tests). Browser reviews:

  - regressions: P1-E5 72 + 6, P1-E4 62 + 8, P1-E3 57 + 8, P1-E2 81,
    P1-E1 40, S2 66, S1A 50 (all PASS)

4. MIGRATION / SCHEMA (20261014000000_icp_lead_scoring.sql)
--------------------------------------------------------------------------------
company_signal_observations
  - company, profile, revision, kind (buying|exclusion), signal_id,
    state (present|absent), note ≤ 500, optional source evidence,
    created_by, observed_at
  - composite FKs (company/profile in the workspace)
  - unique (company, profile, revision, kind, signal)
  - trigger: the signal exists in that kind's list at the profile's
    current revision; evidence belongs to the company
  - RLS members incl. DELETE (unknown); immutable keys
  - index (company_id, icp_profile_id, icp_revision)
lead_scores
  - + input_fingerprint (^[0-9a-f]{64}$), coverage_percent 0–100,
    explanation (≤ 16 KB), effective_weights (≤ 1 KB),
    exclusion_reasons (≤ 50)
  - status adds excluded
  - scored ⇒ score/grade/time/fingerprint/coverage
  - excluded ⇒ no score/grade + time/fingerprint/coverage/≥ 1 reason
  - pre-engine scored rows → stale
public.scoring_input(workspace, company, profile)
  - canonical input document + sha256 fingerprint
public.save_lead_score(...)
  - the only write path: membership, current revision, current
    fingerprint, outcome and threshold-consistent grade checks; upsert per
    revision
public.list_companies
  - recreated: + score_state, coverage_percent; grade/score only when
    current; new grade filters/sort
Indexes: only the observations lookup index; lead_scores keeps its
existing indexes (the list reads the default profile's row via the unique
(company, profile, revision) index).

5. SCORING ENGINE ARCHITECTURE
--------------------------------------------------------------------------------
  DB:     public.scoring_input → canonical document + fingerprint
            (one definition)
  DAL:    parseScoringInput → ScoringInput DTO (zod; invalid ICP sections
            = not configured)
  Engine: evaluateCompanyAgainstIcp(input) → Evaluation (pure; same input →
            same output)
  Record: toScoreRecord → bounded columns → public.save_lead_score
The same evaluator can serve batch evaluation and the Today queue later.
React components never calculate.


--------------------------------------------------------------------------------
6. CONFIGURED-CATEGORY HANDLING
--------------------------------------------------------------------------------
  company_fit         any of industries / size / characteristics / keywords
                      (notes never scored)
  geography_fit       ≥ 1 target geography
  decision_maker_fit  ≥ 1 role
  buying_signal_fit   ≥ 1 enabled buying signal
No scoring model, or no configured category with weight > 0 → "This ICP
does not have enough criteria configured to evaluate companies." (with a
Settings link); nothing is stored.


--------------------------------------------------------------------------------
7. EFFECTIVE WEIGHTS
--------------------------------------------------------------------------------
Denominator = sum of the configured categories' saved weights; contribution
= raw × weight / denominator. Saved weights are never rewritten. Each
category shows its configured weight and its effective share (e.g. 40 →
"effective 50%" when buying signals aren't configured). Unit-tested:
  - every non-empty category combination's shares sum to 100
  - (87.5×40 + 100×20 + 70×20)/80 = 86


--------------------------------------------------------------------------------
8. COMPANY FIT
--------------------------------------------------------------------------------
The average of the configured groups.
  - Industry: an ICP phrase in the company industry or tag evidence → 100;
    otherwise 0; no data → 0 + unknown ("Industry data unavailable" vs
    "doesn't match").
  - Size: inside → 100, overlap → 50, outside → 0; open-ended bounds; no
    data → unknown.
  - Characteristics/keywords: share of phrases found in the corpus (name,
    industry, description, tag evidence); no text beyond the name →
    unknown.
Literal whole-word matching only; no synonyms.


--------------------------------------------------------------------------------
9. GEOGRAPHY FIT
--------------------------------------------------------------------------------
Country / country + region / country + city (+ region when set), normalized
comparison.
  - any match → 100
  - located elsewhere → 0 (known)
  - no country, or too general for the targets → 0 (unknown)
No geocoding, distance or provider calls.


--------------------------------------------------------------------------------
10. DECISION-MAKER FIT
--------------------------------------------------------------------------------
Saved active contacts only ("left company" excluded in scoring_input). P1-E5
whole-word title matching (now a shared helper).
  - best priority: primary 100 · secondary 70 · fallback 40 · none 0
    (known)
  - no contacts → 0 (unknown)
Provider decision-maker flags, seniority and the number of contacts add no
points.


--------------------------------------------------------------------------------
11. SIGNAL OBSERVATIONS
--------------------------------------------------------------------------------
Manually confirmed per company × profile × revision. Unknown = no row
(delete). Validated twice:
  - the server action re-reads the ICP: revision match, enabled signal of
    that kind
  - the DB trigger checks that the signal exists in the profile at its
    current revision
Not copied to new revisions. The note is optional and doesn't affect
scoring (or the fingerprint). Nothing is inferred from text, websites or
providers. "Save signals only" records observations without re-scoring
(the result then reads Outdated).


--------------------------------------------------------------------------------
12. BUYING-SIGNAL SCORING
--------------------------------------------------------------------------------
sum(present weights) / sum(enabled weights) × 100. Absent 0; unknown 0 and
lower coverage; disabled ignored. Signal weights are separate from the
category weight.


--------------------------------------------------------------------------------
13. EXCLUSION HANDLING
--------------------------------------------------------------------------------
Only enabled exclusions observed PRESENT count.
  - hard_exclude → outcome Excluded: no grade, score NULL, reasons stored
    and shown; breakdown kept for explanation
  - penalty → points subtracted (summed, not weighted)
Unknown/absent never exclude. Suppression is untouched.


--------------------------------------------------------------------------------
14. SCORE / GRADE CALCULATION
--------------------------------------------------------------------------------
  final = Math.round(clamp(base − penalties, 0, 100))
  A ≥ a, B ≥ b, else C, using the profile's saved thresholds
save_lead_score rejects a grade inconsistent with the thresholds.
Documented example: 85/100/70/50 with weights 40/20/20/20 → base 78; −10 →
68 → B (unit-tested).


--------------------------------------------------------------------------------
15. DATA COVERAGE
--------------------------------------------------------------------------------
Units:
  industry, size, each characteristic, each keyword, geography, decision
  makers, each enabled buying signal, each enabled exclusion
coverage = round(known / total × 100). It never changes the fit (tested:
same score with coverage 62% vs 100%). "Improve data coverage" names what is
missing and points to Enrich company / Find decision makers / Review
signals; nothing runs automatically.


--------------------------------------------------------------------------------
16. EXPLANATION MODEL
--------------------------------------------------------------------------------
explanation = {
  v, base_score,
  categories: {key: [{criterion, result
               (matched|partial|not_matched|unknown), detail}]},
  exclusions: [...],
  missing: [...]
}
  - ≤ 20 items per list; details ≤ 200 chars; total ≤ 16 KB
  - deterministic template sentences; no HTML, no AI
breakdown holds RAW category percentages + exclusion_penalty (points).
effective_weights = {category: {configured, effective}}.


--------------------------------------------------------------------------------
17. INPUT FINGERPRINT
--------------------------------------------------------------------------------
SHA-256 (PostgreSQL sha256) of the canonical jsonb text of scoring_input:
  - company name/industry/description/employee range/country/region/city
  - sorted distinct tag evidence
  - sorted active-contact titles
  - sorted observations (current revision)
  - ICP id, revision and configuration
jsonb output sorts keys, so the same facts give the same hash.
DB-tested:
  - stable for notes, qualification, contact names/emails and contact
    insertion order
  - changes for industry, description, employee range, location, a contact
    added, a contact title change, a contact leaving, tags, a signal
    observation, and an ICP revision
  - a note edit leaves it unchanged


--------------------------------------------------------------------------------
18. STALE / CURRENT DETECTION
--------------------------------------------------------------------------------
current ⇔ stored revision = current revision AND stored fingerprint =
scoring_input() fingerprint now.
  - Computed on read: drawer (scoreCurrentness) and Leads (list_companies),
    with the same function. No mutation triggers.
  - The drawer explains why: "The profile changed …" vs "Company, contact
    or signal data changed …".
Browser-verified Outdated after:
  - a company change (Enrich company)
  - a contact change (a new decision-maker contact)
  - a signal change (Save signals only)
  - an ICP revision change
In each case Recalculate made the result current again.


--------------------------------------------------------------------------------
19. LEAD-SCORE PERSISTENCE
--------------------------------------------------------------------------------
Only through save_lead_score.
  - The action accepts ids and observation choices only (strict schemas;
    unit-tested that score/grade/breakdown/coverage/fingerprint keys are
    rejected).
  - The server reads the inputs, evaluates and saves.
  - The function rejects stale revisions/fingerprints and threshold-
    inconsistent grades.
  - Same revision → update in place (no duplicates); new revision → new
    row; old rows readable (DB-tested).
  - Direct table writes are still denied.

27. CODE-QUALITY REVIEW
--------------------------------------------------------------------------------
Verified
  Q1  Deterministic scoring: a pure engine, no clock/I/O; a determinism
      test.
  Q2  Configured categories / effective weights: excluded from the
      denominator; saved weights untouched; all combinations tested.
  Q3  Coverage semantics: separate units; never alters fit (tested).
  Q4  Text matching: one literal whole-phrase helper (scoring + P1-E5
      roles).
  Q5  Geography: structured, specificity-aware, unknown vs no-match
      distinguished.
  Q6  Role matching reuse: same helper and priority order as contact
      discovery.
  Q7  Signal observations: structured, revision-pinned, validated by the
      DB and the action; unknown = no row.
  Q8  Hard exclusions / penalties: present-only; Excluded has no grade;
      penalties in points.
  Q9  Thresholds: saved values only; DB re-checks grade consistency.
  Q10 Fingerprint: one canonical definition in the DB, used for both
      evaluation and the list; equality/inequality DB-tested.
  Q11 Stale detection: computed on read; no fragile triggers.
  Q12 Persistence: a single checked write path; ids-only browser input.
  Q13 Multiple ICPs: per profile/revision; default profile for Leads.
  Q14 Separation: qualification and suppression never changed
      (browser-checked for qualification).
  Q15 Client/server: the engine runs in server actions; the client renders
      view models only.
Follow-ups
  F1 (Med)  A member with direct API access can call save_lead_score with
            fabricated values that match the current fingerprint (the
            function blocks stale/inconsistent rows, not deliberate
            tampering by an authorized member). Moving the engine into a
            trusted server path (service role) or into SQL would close
            this; acceptable under the collaborative model for now.
  F2 (Med)  list_companies computes scoring_input() for every company that
            has a current-revision result on each Leads request. Fine at
            MVP scale; for large workspaces consider caching the current
            fingerprint or a materialized "inputs changed at" marker.
  F3 (Low)  Observation history: changing an observation overwrites it
            (the prior state is only implied by older score rows); a
            history table may be wanted later.
  F4 (Low)  Industry matching is one-directional (an ICP phrase must appear
            in the company's industry/tags), so a company industry "Data"
            doesn't match the ICP's "Data analytics". This is deliberate:
            fewer false positives.
  F5 (Info) No batch "Evaluate visible leads" (single-company only; same
            engine ready for batch).
  F6 (Info) Carried: no CSP; forbidden pages return HTTP 200;
            my_workspace_ids() RLS helper planned.
