1. SUMMARY
--------------------------------------------------------------------------------
Users can now fill the lead core in two controlled ways.
  - Leads → Add leads → Add manually: a company, optionally with a first
    contact. It goes through the same normalization, validation and duplicate
    rules as imports. A same-domain company can't be added twice; weaker
    matches warn first. The drawer gained Add contact and do-not-contact
    controls.
  - Leads → Add leads → Import CSV: a staged workflow, Upload → Map → Review
    (validate, match, decide merge/skip/create) → Import (chunked, one
    transaction per row) → Report. Nothing reaches companies/contacts until
    the user presses "Import N rows". Rows can't be committed twice.
  - Evidence: manual and CSV evidence for every non-empty field. CSV evidence
    is traceable to its import batch and row.
  - Leads page: real server-side pagination (25 per page), basic filters
    (qualification, grade, restriction, has contacts, country) and sorts
    (updated, name, qualification, grade), all in the URL.
  - No discovery, providers, enrichment, scoring, calling, email or campaigns.
Quality gate: npm.cmd run verify EXIT 0 (264/264 tests). Browser reviews:
P1-E2 81/81, with regressions P1-E1 40/40, S2 66/66 and S1A 50/50. The import
RLS/constraint mutation check detected every break.

4. MIGRATION / SCHEMA (20261010000000_manual_csv_ingestion.sql)
--------------------------------------------------------------------------------
New: import_batches, import_rows; lead_sources.import_batch_id/import_row_id;
functions ingest_lead, stage_import_rows, list_companies; triggers
guard_import_batch, guard_import_row (+ updated_at and immutable-key triggers).
All relationships are composite same-workspace FKs. RLS is on, with
column-level grants, nothing for anon, no DELETE. Functions are SECURITY
INVOKER with search_path='' and are not executable by anon.
Indexes (each tied to a query):
  import_batches (workspace_id, created_at desc)   recent imports
                 (workspace_id, status)
  import_rows    UNIQUE (import_batch_id, row_number)
                 (import_batch_id, match_state)    review filters
                 (import_batch_id, row_number) WHERE commit_result IS NULL
                                                   next commit chunk
  lead_sources   (import_batch_id) WHERE NOT NULL  traceability
Not added: separate decision/commit_result indexes. Filtering happens on one
batch's rows (≤ 5,000), which the batch_match index already narrows.
P1-E1 identity rules are unchanged; the unique active domain index remains
the backstop.


--------------------------------------------------------------------------------
5. IMPORT BATCHES
--------------------------------------------------------------------------------
Columns: filename, status, headers (1–100), mapping, total_rows (≤ 5000),
valid/invalid/created/merged/skipped/failed counts, created_by, created_at,
updated_at, completed_at, archived_at.
State model (kept small; no background-job infrastructure):
  mapping ⇄ review → processing → completed
  mapping/review → cancelled
The spec's "uploaded", "ready" and "failed" states were not needed. Upload
creates the batch directly in mapping; "ready" is review with decisions; a
row-level failure never fails the batch. Completed/cancelled are terminal and
frozen by trigger (only archived_at may change). completed is reachable only
from processing and requires completed_at.


--------------------------------------------------------------------------------
6. IMPORT ROWS
--------------------------------------------------------------------------------
row_number (unique per batch); raw_data (cell strings, ≤ 16 KB);
normalized_data {mapped, company, contact} (≤ 16 KB); validation_errors
[{level, field, message}] (≤ 8 KB); match_state; match_reason;
matched_company_id / matched_contact_id / matched_import_row_id (earlier row
of the same file); decision; commit_result; commit_notes (≤ 8 KB);
committed_company_id / committed_contact_id.
CHECKs: an invalid row can only be skipped; created/merged ⇒ committed
company. A row with a commit_result is frozen by trigger, as is every row of
a terminal batch.


--------------------------------------------------------------------------------
7. CSV PARSING
--------------------------------------------------------------------------------
Papa Parse 5.7 (mature parser), dynamicTyping off: values stay text, so
formulas such as "=SUM(A1)" are literal strings.
Handled and tested:
  - BOM; quoted commas; quoted line breaks; escaped quotes; CRLF/LF/CR
  - blank rows (dropped)
  - duplicate/blank headers ("Email (2)", "Column 3")
  - short rows (padded) and long rows (trimmed)
  - unclosed quote → rejected
  - UTF-8, falling back to Windows-1252
Limits (src/lib/imports/limits.ts):
  - .csv only; 5 MB file; 5,000 rows; 100 columns; 1,000 characters per cell
  - Name and size are checked in the browser AND on the server. The
    browser-reported MIME type is not trusted. The Server Action body limit
    is 6 MB.
Lifecycle: the file is read into server-action memory, parsed and discarded.
Vleeds never writes it to disk or storage. Only parsed cells are staged.
XLS/XLSX: not supported (message suggests saving as CSV).


--------------------------------------------------------------------------------
8. COLUMN MAPPING
--------------------------------------------------------------------------------
Every column → a Vleeds field (14 company + 9 contact fields, exactly the
spec list) or "Ignore this column". Suggestions come from generic header
synonyms; sample values are shown; ignored columns need no action. Each field
can be used once (flagged inline). Company name is required (the P1-E2
product decision). The mapping is saved on the batch; there is no reusable
mapping-template system (out of scope). "Back to mapping" re-stages
everything from raw_data.


--------------------------------------------------------------------------------
9. NORMALIZATION
--------------------------------------------------------------------------------
No new algorithms. Rows are validated and normalized through the P1-E1
lead-core Zod schemas, which call src/lib/lead-core/normalize.ts: domain
(from domain, or derived from the website), company name, email, person name
and international phone. The display/original values are kept (canonical
name, phone as entered, email as entered). Locations: ISO code or English
country name → ISO code; region, city, postal code and address lines are
trimmed text. Qualification and seniority accept keys or labels.


--------------------------------------------------------------------------------
10. VALIDATION
--------------------------------------------------------------------------------
Every row is labelled Valid / Warning / Error, with per-field messages.
  Errors: missing company name (including contact-only rows); invalid
    website/domain/email/profile URL; employee min > max or not a whole
    number; cell > 1,000 chars; contact without a name; oversized row
  Warnings: unknown country, unsupported qualification/seniority (left
    out); website/domain host mismatch; national phone (not comparable)
One bad row never rejects the file. Invalid rows can only be skipped
(DB CHECK). Contact-only rows are invalid: no orphan contacts.


--------------------------------------------------------------------------------
11. DUPLICATE DETECTION
--------------------------------------------------------------------------------
Reuses matchCompany / matchContact (src/lib/lead-core/dedupe.ts) with the
P1-E1 hierarchy. It runs against existing active companies AND earlier rows
of the same file.
  matched (provider id / domain)       suggest Merge; allowed Merge, Skip
  possible_duplicate (intl phone,      no suggestion; allowed Merge, Skip,
    name + same place)                 Create new
  new                                  suggest Create; allowed Create, Skip
  invalid                              Skip only
Low-confidence matches are never merged automatically. "Create new" is not
offered for a domain match; the compare sheet explains why (the domain rule
was not weakened). Contacts are matched at commit time against current data:
email = same person; same name at the company = merged with a note; an email
owned at another company blocks the contact (noted). Manual entry uses the
same matchCompany: same domain → blocked with Use existing; weaker →
"Add as a separate company" after confirmation.


--------------------------------------------------------------------------------
12. MERGE BEHAVIOUR (exact rules; product doc §4)
--------------------------------------------------------------------------------
  1 A blank imported value never changes anything.
  2 Imported values fill empty fields only.
  3 Equal values (case-insensitive; normalized phone; trailing slash) need no
    change.
  4 Conflicting populated values: the existing value is kept, the conflict is
    written to the row's notes, and the imported value is still appended as
    evidence.
  5 Names are never changed by a merge.
  6 Location is filled only when empty.
  7 Employee range: empty ends are filled unless that would make min > max.
  8 Qualification is applied only while the company is "unreviewed".
Contacts follow rules 1–5.

13. MANUAL COMPANY ENTRY
--------------------------------------------------------------------------------
Add leads → Add manually opens a canonical sheet (ConfigSheet). Fields:
  - name (required), website, primary domain, phone
  - country / region / city, employee min / max, notes
  - optional first contact (name, title, email, phone)
Server-side Zod validation, inline field errors. Duplicate check before
saving (§11). The company, contact and evidence are written as one
transaction through ingest_lead, then the drawer opens on the new company.
Edit company was NOT implemented, to keep the story focused (see §27).


--------------------------------------------------------------------------------
14. MANUAL CONTACT ENTRY
--------------------------------------------------------------------------------
Company drawer → Add contact. Fields: full name (or first/last), title,
seniority, email, phone, profile URL, notes, primary contact.
  - An existing email is refused (case-insensitive).
  - The same name at the company asks "Add anyway".
  - The primary checkbox is disabled when a primary exists; the server
    checks too, and the DB unique index is the backstop.
  - The first contact of a company becomes primary.


--------------------------------------------------------------------------------
15. SOURCE EVIDENCE
--------------------------------------------------------------------------------
One lead_sources row per NON-EMPTY observed field. Manual entry uses
source_kind=manual; CSV commits use source_kind=csv with provider_key null.
CSV rows also carry import_batch_id + import_row_id (nullable, composite
same-workspace FKs, immutable). Keys: company.name / website / domain /
phone / location / employee_range and contact.name / title / seniority /
email / phone / linkedin. Values are single field values, ≤ 2 KB (P1-E1
CHECK), never the whole row. For merges, conflicting imported values are
still recorded as evidence. "Which import created/updated this company?" is
answered via lead_sources.import_batch_id or import_rows.committed_company_id.


--------------------------------------------------------------------------------
16. COMMIT / IDEMPOTENCY
--------------------------------------------------------------------------------
  - "Import N rows" (N = create + merge decisions) moves review → processing.
    Only one such update can succeed, so a double click can't start two
    imports.
  - The page then calls continueImport repeatedly. Each call commits the next
    100 uncommitted rows in file order, ONE TRANSACTION PER ROW
    (ingest_lead), and announces progress. A failure marks only that row
    "failed" with a fixed, safe message; earlier rows stay committed.
  - A reload while processing resumes automatically.
  - Merges into a company created earlier in the same file use that row's
    result. If that row was skipped or failed, the later row creates the
    company instead.
  - Four guards against committing twice: (1) the planner ignores rows with
    a result; (2) ingest_lead locks the row FOR UPDATE, returns the recorded
    result if present, and requires the batch to be processing; (3) a trigger
    freezes committed rows; (4) completed/cancelled batches are frozen.
  - After completion there is no Import action (verified after reload).
Practical limit: a 5,000-row file = 50 chunk requests. That is fine on a
normal connection, but the tab must stay open (reopening resumes). There is
no job queue (not needed for the MVP).


--------------------------------------------------------------------------------
17. IMPORT REPORTING
--------------------------------------------------------------------------------
Report: Total rows, Created, Merged, Skipped, Invalid, Failed. The row list
has views All / Created / Merged / Skipped / Invalid / Failed (50 per page).
Each row shows its outcome, decision, a link to the company and notes
(conflicts kept, contact not imported, failure reason). Leads → Import CSV
lists recent imports with their status. Import history can't be deleted from
the UI; Cancel (with a confirmation step) marks a batch cancelled. No
analytics.

25. CODE-QUALITY REVIEW
--------------------------------------------------------------------------------
Verified
  Q1  Workspace ownership: both new tables have an immutable workspace_id.
      Every link (batch, matched/committed company and contact, matched row,
      evidence → batch/row) is a composite same-workspace FK (tested).
  Q2  Import relationships: rows can't move between batches (immutable key);
      row numbers are unique per batch; raw_data is immutable.
  Q3  Duplicate decisions: allowed decisions are enforced server-side

      can't be created separately (app rule + unique index backstop).
  Q4  Commit idempotency: four layers (§16), tested in DB and unit tests.
  Q5  Manual-entry normalization: the same Zod schemas and normalize.ts as
      CSV; the same matchCompany; the same ingest_lead.
  Q6  Evidence relationships: only non-empty single-field values, ≤ 2 KB,
      append-only, import references same-workspace and immutable.
  Q7  Restrictions: P1-E1 role rules unchanged (RLS); member UI explains.
  Q8  Upload limits: extension and size checked server-side; MIME type not
      trusted; row/column/cell limits; Server Action body limit 6 MB; content
      is parsed as text only.
  Q9  Input validation: every action authenticates, re-authorizes the
      workspace (findWorkspace), UUID-checks ids, validates with Zod and maps
      DB errors to fixed messages (no internal details reach the user).
  Q10 Client/server boundary: no browser DB client. Client components get
      DTOs. Papa Parse is server-only (checkCsvFile moved to a parser-free
      module). Bundle scan clean.

      (decision labels rendered blank in the report). Moved to
      src/lib/imports/classify.ts; the browser check now asserts it.
  R2  Duplicate DOM ids for decision selects (table + card) → useId.
  R3  One-tap irreversible "Cancel import" next to the primary action →
      confirmation step.
  R4  Add leads menu overflowed at 360px (right-aligned to a left-aligned
      button) → left-aligned on phones.
  R5  Step indicator overflowed on phones → compact labels.
  R6  Filter selects 40px on phones → 44px.
Follow-ups
  F1 (Low)  Review pages load all of a batch's rows (≤ 5,000, ≤ ~16 KB each,
            in 1,000-row requests) to compute counts and filter. Fine for the
            MVP limit; move counts/filters into SQL if limits grow.
  F2 (Low)  ingest_lead is callable by any member through the API, with
            arbitrary (but CHECK-constrained, RLS-scoped) values, which is

  F3 (Low)  A decision can still be changed in the instant between "Import"
