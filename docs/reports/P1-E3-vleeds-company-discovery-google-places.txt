1. SUMMARY
--------------------------------------------------------------------------------
Discover is now active:
  - ICP → Discovery run → Provider → Candidate references → Review.
  - A member picks an ICP (the default is preselected), confirms or edits
    what they are looking for, picks one of the ICP's geographies (or
    another location, or none) and a page size, then presses Find
    companies.
  - Vleeds calls Google Places API (New) Text Search on the server and
    shows the results with Google Maps attribution.
  - Each result's Vleeds status (New reference / Seen before / Existing
    company) comes from durable data only.
  - The user can Select, Dismiss or Undo, Load more one page at a time,
    then finish or cancel. Usage (requests/candidates for this search and
    this month) is shown.
  - Recent discovery activity lists past searches, with Retry for failed
    ones.
  - A generic, server-only provider layer (interface, capabilities, per-field
    retention, registry) keeps Google-specific code in one folder.
  - Place IDs are the only Google data stored. Selected references become
    needs_enrichment (or "selected" when already an existing company). No
    company is created from Google content.
  - Not done (by design): Place Details, enrichment, Apollo, scoring,
    background/bulk discovery, calling, email, campaigns.
Quality gate: npm.cmd run verify EXIT 0 (308/308 tests). Browser reviews:
P1-E3 not-configured 8/8 and configured 56/56, with regressions P1-E2
81/81, P1-E1 40/40, S2 66/66 and S1A 50/50.

4. MIGRATION / SCHEMA (20261011000000_company_discovery_foundation.sql)
--------------------------------------------------------------------------------
Tables: discovery_runs, discovery_candidates, provider_usage_events. All are
workspace-owned (cascade), RLS on, column-level grants, nothing for anon, no
DELETE.
Relationships (composite, same workspace):
  run → icp_profiles (workspace_id, id)
  candidate → run (workspace_id, run_id, provider_key)
  candidate → companies
  usage → run
Triggers:
  - guard_discovery_run: completed/cancelled are final
  - guard_discovery_candidate: candidates of final runs frozen; stamps
    decided_by/at
  - refresh_discovery_counts: SECURITY DEFINER, search_path=''; recomputes
    counts, which have no API grant
  - updated_at; immutable keys (query, geography, provider, ICP reference,
    page size, provider id)
Indexes:
  discovery_runs        (workspace_id, created_at desc) · (icp_profile_id)
                        WHERE NOT NULL
  discovery_candidates  UNIQUE (discovery_run_id, provider_key,
                        external_record_id) · (discovery_run_id, position)
                        · (workspace_id, provider_key, external_record_id)
                        ["seen before"]
  provider_usage_events (workspace_id, occurred_at desc) ·
                        (discovery_run_id) WHERE NOT NULL
Not added: a (workspace_id, status) run index. History reads the latest 10
by created_at. A provider_key + occurred_at index isn't needed while usage is
read per workspace.

5. PROVIDER ABSTRACTION
--------------------------------------------------------------------------------
CompanyDiscoveryProvider exposes:
  - providerKey, label, attribution {text, rankingNote}
  - isConfigured()
  - getCapabilities()
  - searchCompanies(input)
  - normalizeCandidate(raw)
Capabilities: companyDiscovery, durableExternalId, durableCompanyFields,
supportsPagination, supportsTextQuery, supportsGeographyText, maxPageSize,
and fieldRetention (per field: durable | transient).
Candidates carry providerKey, externalId, display {name, address, category},
sourceUrl, attributions and fieldRetention.
Results are generic: {ok, candidates, nextCursor, usage} or {ok:false,
code, usage|null}. Status categories are ok, empty, timeout, rate_limited,
setup, invalid_request, unavailable, malformed (+ not_configured).
Registry (server-only): DEFAULT_DISCOVERY_PROVIDER = google_places;
getDiscoveryProvider(key). Pages, actions, DAL and UI never see Google
request/response shapes. A business-agnostic test enforces that provider
names appear only in their adapter folder.


--------------------------------------------------------------------------------
6. GOOGLE PLACES ADAPTER
--------------------------------------------------------------------------------
Places API (New) Text Search only:
  POST https://places.googleapis.com/v1/places:searchText
  Headers: Content-Type: application/json, X-Goog-Api-Key,
  X-Goog-FieldMask
No legacy API, no Place Details, no wildcard mask.
  - Timeout: 10 s via AbortController.
  - Retry: one bounded retry, only for network errors, timeouts and 5xx;
    quota, permission and invalid errors are never retried. Both requests
    are counted.
  - The key goes only in a header, is read only from GOOGLE_PLACES_API_KEY
    (server-only), and is never logged or returned.
  - GOOGLE_PLACES_ENDPOINT (dev/review only) is accepted only for loopback
    hosts and ignored when VERCEL_ENV=production (unit-tested).


--------------------------------------------------------------------------------
7. SEARCH REQUEST MODEL
--------------------------------------------------------------------------------
Generic input: {query, geography (structured), pageSize, cursor?,
languageCode?, regionCode?}.
The Google body is {textQuery: "<query> in <city, region, country>",
pageSize 1–20, pageToken?, regionCode = geography country}.
Server-side validation (Zod, strict):
  - query: 2–120 characters, whitespace collapsed
  - geography: {kind: icp, id} | {kind: custom, countryCode (ISO), region?,
    city?} | {kind: none}
  - pageSize: 5 | 10 | 20
  - cursor: printable, ≤ 4 KB
The ICP profile and its geography are re-read on the server by id; the
browser never supplies geography text for ICP geographies.


--------------------------------------------------------------------------------
8. FIELD MASK
--------------------------------------------------------------------------------
googlePlacesDiscoveryFieldMask (google-places/fields.ts, the only place):
  places.id,places.displayName,places.formattedAddress,places.primaryType,
  places.attributions,nextPageToken
Per Google docs (checked 2026-10-08):
  - id, attributions, nextPageToken → Text Search Essentials (IDs Only)
  - displayName, formattedAddress, primaryType → Text Search Pro
  - so each request is expected to be billed as Text Search Pro. This is
    recorded as sku_hint.
No prices are coded (pricing_reference = Google's pricing page). Not
requested: phone, website, ratings, reviews, photos, hours, prices,
summaries. A unit test pins the mask.


--------------------------------------------------------------------------------
9. ICP INTEGRATION
--------------------------------------------------------------------------------
  - The default profile is preselected; any active profile can be chosen.
  - Its industries/categories and keywords appear as suggestions; the query
    is prefilled with the first one and stays editable.
  - Its target geographies are the first "Where" options.
  - Nothing runs until Find companies is pressed. There is no AI query
    generation and no scoring.
  - The run records icp_profile_id + icp_revision.
  - A workspace without a profile can still search with a typed location.


--------------------------------------------------------------------------------
10. GEOGRAPHY HANDLING
--------------------------------------------------------------------------------
Geography reuses the ICP target-geography structure (countryCode,
countryName, region, city, label) and stays structured through to the adapter
(DiscoveryGeography). The Google adapter composes text from the parts that
exist and sends the country as regionCode. There is no geocoding dependency.
The searched geography is stored on the run as Vleeds data (≤ 2 KB).


--------------------------------------------------------------------------------
11. DISCOVERY RUNS
--------------------------------------------------------------------------------
Statuses:
  running → review (page loaded)
  running → failed (first page failed; error_code = category)
  review → running (Load more)
  failed → running (Retry)
  review → completed (Done reviewing)
  running/review/failed → cancelled
Completed and cancelled are final. Each transition is a filtered update
("only from …"), so double clicks can't race. The run also stores
pages_loaded, has_more (a flag, not the token) and counts.


--------------------------------------------------------------------------------
12. DISCOVERY CANDIDATES
--------------------------------------------------------------------------------
Each candidate holds:
  - external_record_id (Place ID) + provider_key
  - position (Vleeds order within the run)
  - match_state, match_company_id
  - decision, decided_by/at
There are NO provider content columns (a DB test asserts this). One row per
provider id per run; the same Place ID may appear in other runs (tested).
Repeats across pages are ignored (insert … on conflict do nothing).


--------------------------------------------------------------------------------
13. PROVIDER-DATA RETENTION MODEL
--------------------------------------------------------------------------------
  Durable:
    - Place ID
    - run metadata (query, geography, ICP reference, page size, status,
      counts, timestamps)
    - decisions
    - usage events
  Transient:
    - name, address, primary type, third-party attributions (server memory
      + the browser's state for the open search)
    - nextPageToken (browser ↔ server round trip only)
  Never stored or shown:
    - raw responses
    - Google error bodies (reduced to a status category)
After a reload, history shows queries and counts only (browser-verified).
The capability model makes this explicit per provider, so a future
durable-data provider can declare durable fields without schema changes.


--------------------------------------------------------------------------------
14. CANDIDATE DECISIONS
--------------------------------------------------------------------------------
  - Select on a new or seen-before reference → needs_enrichment
  - Select on an existing company → selected (the DB requires a linked
    company)
  - Dismiss → dismissed
  - Undo → unreviewed
Decisions are validated server-side (Zod enum); only open runs accept them.
The DB enforces the state list, the frozen state of final runs and the
decided_by stamp. No company is created from transient fields.


--------------------------------------------------------------------------------
15. EXISTING-COMPANY IDENTITY MATCHING
--------------------------------------------------------------------------------
Before showing a candidate:
  - Vleeds looks up lead_sources for provider_key = google_places AND
    external_record_id = Place ID, restricted to active companies of the
    workspace → "Existing company", with a link to the company drawer.
  - Other runs' candidates → "Seen before".
  - Otherwise → "New reference".
Names and addresses are never used for matching, so there is no hidden
dedupe database. Browser-verified with a mock link, which also shows that
another workspace doesn't see it. Those lead_sources links will be written
by the later, approved enrichment/ingestion step (P1-E4); none are created
in P1-E3.


--------------------------------------------------------------------------------
16. PROVIDER USAGE ACCOUNTING
--------------------------------------------------------------------------------
One provider_usage_events row per request batch. Columns: provider_key,
operation (text_search), requested_fields (mask), request_count (1, or 2
with the retry), result_count, status, sku_hint, pricing_reference,
estimated_cost_micros (NULL), occurred_at, created_by. Append-only. Never a
key, token or payload. No event is recorded when the provider isn't
configured, because no request is made.
UI: "This search: Google Places · N requests · M candidates", plus "This
month: N requests". There are no money amounts: there is no reliable local
price.

  (1) Find companies form, or the calm not-configured panel
  (2) Results: table on md+, cards on phones; columns Company, Location,

--------------------------------------------------------------------------------
19. PAGINATION / LOAD MORE
--------------------------------------------------------------------------------
One page per explicit action. nextPageToken travels to the browser and back
(validated) and is never stored. The run keeps has_more and pages_loaded. A
failed Load more keeps earlier results. Google's 60-results-per-query cap
applies. There is no automatic multi-page consumption.


--------------------------------------------------------------------------------
20. PROVIDER ERRORS
--------------------------------------------------------------------------------
Each case gets a calm, fixed message (docs/providers/google-places.md §6):
  - not configured · timeout · rate/quota · setup/billing/permission
  - invalid request · temporarily unavailable · unreadable response
  - storage failure · no results
No raw bodies or codes are shown (browser-verified). A failed first page
marks the run failed, with Try again in the results and Retry in history.
There are no automatic loops beyond the one bounded retry. The rest of
Vleeds is unaffected; Discover itself loads without a key.

26. CODE-QUALITY REVIEW
--------------------------------------------------------------------------------
Verified
  Q1  Provider abstraction: the rest of Vleeds uses only types.ts and
      registry.ts. A test confines provider names to their adapter folder.
  Q2  Google isolation: the request/response shape, field mask, SKU hint,

      across runs.
  Q6  Usage accounting: every request is recorded (including failures and
      retries); append-only; nothing sensitive.

      calls server actions only. The bundle scan checks for the key name,
      the endpoint and the field-mask header. The browser made no Google
      or Supabase requests.
  Q8  Environment: the key is never NEXT_PUBLIC_, read at request time and
      never logged. The endpoint override is loopback-only and refused in
      production. There is no startup failure without a key.
  Q9  Errors: categories → fixed messages; raw bodies are discarded;
      timeout; one bounded retry.
  Q10 Input: Zod on every action; the ICP and geography are re-read
      server-side by id; the cursor is bounded; UUIDs are checked; run
      transitions are filtered.
Follow-ups
  F1 (Low)  There is no per-user or per-workspace rate limit beyond
            explicit clicks and Google quotas. Consider a daily request
            budget per workspace before wider rollout.
  F2 (Low)  The usage totals query reads up to 5,000 events of the month
            and sums them in memory. Move it to SQL if volume grows.
  F3 (Low)  The "This search" totals count only the current month's
            events. A run that spans a month boundary would under-count.
            Cosmetic.
  F4 (Low)  There is no Google Maps logo asset; the text attribution is
            used. Revisit if a logo is preferred.
  F5 (Info) Carried: no CSP; forbidden pages return HTTP 200; RLS helper
