1. SUMMARY
--------------------------------------------------------------------------------
A Next.js 16 + TypeScript + Supabase application foundation with:

  - database-enforced multi-tenancy (organizations -> memberships -> workspaces)
  - deny-by-default privileges and Row Level Security on every table
  - 36 adversarial tenant-isolation tests (plus 9 unit tests), all passing
  - an authenticated, responsive application shell with a cross-organization
    workspace switcher and placeholder Today / Discover / Leads / Campaigns /
    Settings sections, including loading, empty, error and not-found states
  - zero Supabase credentials or calls in the browser; all data access is
    server-side through one Data Access Layer under the user's own session
  - no business-specific logic: businesses exist only as workspace data,
    enforced by an automated guard test

Not done in this story, by design: lead discovery, enrichment, calling,
provider APIs, billing, public sign-up.

and service_role only).

  updated_at, UNIQUE (organization_id, slug), index on organization_id

5. RLS POLICIES AND PRIVILEGES
--------------------------------------------------------------------------------
RLS is ENABLED on organizations, memberships and workspaces (all public tables).

Privileges (deny by default):
  anon:           nothing on any table or function
  authenticated:
    organizations  SELECT; UPDATE (name, slug)
    memberships    SELECT, DELETE; INSERT (organization_id, user_id, role); UPDATE (role)
    workspaces     SELECT; INSERT (organization_id, name, slug, description,
                   website_url, primary_domain, logo_url, settings);
                   UPDATE (name, slug, description, website_url, primary_domain,
                   logo_url, settings, archived_at)
  service_role:   all (bypasses RLS; not used by the application)
  Local config: auto_expose_new_tables = false

Policies (all TO authenticated):
  organizations_select_member       SELECT  is_org_member(id)
  organizations_update_admin        UPDATE  has_org_role(id, owner|admin)  [using + check]
  (no INSERT policy: use create_organization; no DELETE policy in P0)

  memberships_select_same_org       SELECT  is_org_member(organization_id)
  memberships_insert_admin          INSERT  owner, OR admin AND role <> 'owner'
  memberships_update_admin          UPDATE  owner, OR admin AND role <> 'owner' [using + check]
  memberships_delete_admin_or_self  DELETE  self, OR owner, OR admin AND role <> 'owner'

  workspaces_select_member          SELECT  is_org_member(organization_id)
  workspaces_insert_admin           INSERT  has_org_role(organization_id, owner|admin)
  workspaces_update_admin           UPDATE  has_org_role(organization_id, owner|admin) [using + check]
  (no DELETE policy in P0: archive via archived_at)

6. TESTS EXECUTED
--------------------------------------------------------------------------------
A. Tenant-isolation suite: tests/db/tenancy.test.ts (36 tests)
   Each attempt runs in a transaction with SET LOCAL ROLE and
   request.jwt.claims, exactly as PostgREST does, and is always rolled back;
   denied writes are re-checked as the DB owner.
   - schema hardening (4): RLS on every public table; no anon privileges;
     private helpers not executable by anon; search_path pinned on every
     SECURITY DEFINER function
   - anonymous (5): cannot read any of the 3 tables, call create_organization,
     or insert
   - cross-organization reads (8): by id; by organization_id; via join;
     membership listing; outsider sees nothing; multi-org user sees exactly
     the union; helper functions deny foreign org/workspace
   - cross-organization writes (11): create workspace in foreign org; update
     foreign workspace/org; add self to foreign org (member/admin/owner);
     outsider self-join; delete/alter foreign memberships; MOVE a workspace
     to another org (incl. when the caller owns both); re-point a membership's
     org/user; spoof created_by; direct org insert; delete org/workspace
   - roles (5): member restrictions; admin capabilities; admin cannot
     create/modify/remove owners or self-promote; last owner cannot
     leave/demote; member can leave and then loses access
   - organization creation (2): creator becomes sole owner; invalid slug
     rejected
   - service role (1): bypasses RLS (documents why it must stay server-side)

B. Mutation check of the suite: a temporary migration replaced the workspace
   SELECT policy with USING (true) and disabled RLS on memberships.
   Result: 12 tests FAILED (as required), then the file was removed.

C. Unit tests (9): env validation incl. secret-key rejection; navigation
   (paths, section preservation, UUID validation, open-redirect protection);
   slug rules match the DB constraint; business-agnostic guard (no named
   businesses or specific providers in src/, migrations or seed).

D. Static checks: ESLint; `next typegen && tsc --noEmit`; `next build`.

E. Client-bundle secret scan: scripts/check-client-bundle.mjs over
   .next/static. Canary check: a planted sb_secret_ value and a
   SUPABASE_SERVICE_ROLE_KEY reference were both detected (exit 1); the canary
   was then removed.

F. Browser/end-to-end smoke checks (scripts/ui-review/review.mjs, headless
   Chrome against the production build + UI-review mock backend), 22 checks:
   unauthenticated redirects (/, workspace route, /workspaces/new -> 307
   /login with safe ?next); security headers; generic bad-password error;
   sign-in lands on workspace; switcher groups by org; switching preserves
   the section and updates the active workspace; "/" honours the last-
   workspace cookie; signed-in /login bounce; sign-out and post-sign-out
   lockout; foreign / nonexistent / malformed workspace -> identical
   "Not available"; single-org user's switcher excludes foreign workspaces;
   mobile has no horizontal overflow; no-membership user -> onboarding;
   browser made ZERO requests to Supabase; no secrets in 279 browser-visible
   responses; session tokens never appear in HTML/RSC payloads.

9. ARCHITECTURE DECISIONS (full table: docs/architecture/vleeds-tenancy.md §9)
--------------------------------------------------------------------------------
AD-1  Organization = tenant; workspace = a business inside it.
AD-2  Access via org membership only; per-workspace ACL deferred (can be added
      inside private.is_workspace_member without changing table policies).
AD-3  SECURITY DEFINER helpers in an unexposed `private` schema.
AD-4  Tenant keys immutable (trigger + no column grant), not just policy-checked.
AD-5  No browser Supabase client; all data access server-side via the DAL.
AD-6  Workspace id in the URL; no server-side "current workspace" state.
AD-7  Missing and forbidden workspaces are indistinguishable.
AD-8  No deletes of organizations/workspaces in P0 (archive instead).
AD-9  DB tests portable: PGlite + Supabase shim, or real Supabase via env var.
AD-10 Keep Next.js 16 Cache Components; Supabase work forced to request time.
Also: a "lead" will be a company within a workspace (no separate leads table);
business criteria are versioned, validated jsonb; provider integrations are
generic adapters chosen per workspace; provider secrets go in Supabase Vault.
