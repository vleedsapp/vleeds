1. SUMMARY
--------------------------------------------------------------------------------
A company with a durable domain now has "Find decision makers" in the company
drawer:
  company domain + the selected ICP's decision-maker roles (or titles typed
  for this search) → ONE explicit Hunter Domain Search (≤ 10 people, one
  page, "estimated up to 1 credit") → candidate review → Select / Dismiss /
  Undo → "Save N contacts" → contacts written through the existing contact
  matching and ingest_lead path, with Hunter evidence.
Each candidate shows:
  - transparent role-match labels (Primary/Secondary/Fallback title match,
    Hunter decision maker, Executive seniority)
  - email status and Hunter confidence as reported, kept separate
  - Existing contact / Possible duplicate / Contact already belongs to
    another company / Restricted
Selection is never automatic, and there are no automatic second searches or
pages. Company and person responsibilities stay separate (no company
evidence is written). A generic ContactDiscoveryProvider contract keeps
Hunter's Domain Search shapes inside one adapter folder, which reuses the
P1-E4 Hunter client.
Also closed: P1-E4 F1 (at most one OPEN enrichment run per discovery
reference: DB index + the start action returns the open run).
Not done (by design): Multi-Domain Search, Email Finder, Email Verifier,
Email/Combined Enrichment, Apollo, scoring, outreach of any kind, Today
changes.
Quality gate: npm.cmd run verify EXIT 0 (403/403 tests). Browser reviews:
  - P1-E5: configured 72/72, not configured 6/6
  - regressions: P1-E4 62/62 + 8/8, P1-E3 57/57 + 8/8, P1-E2 81/81,
    P1-E1 40/40, S2 66/66, S1A 50/50

4. MIGRATION / SCHEMA (20261013000000_contact_discovery_hunter.sql)
--------------------------------------------------------------------------------
  - F1 index: company_enrichment_runs_one_open_per_candidate (§5).
  - contact_discovery_runs:
      · company (composite FK, cascade); ICP + revision (composite FK, set
        null)
      · provider; domain (normalized); status
        (draft|searching|review|completed|cancelled|failed)
      · selected_titles jsonb (≤ 10, ≤ 4 KB); decision_maker_only;
        requested_limit 1–10
      · trigger-maintained counts (result/selected/dismissed/saved; no
        grant); error_code; timestamps
  - contact_discovery_candidates:
      · minimal professional fields, verification/confidence, source summary
      · role_match, match_state, matched/committed contact,
        decision + selected_action, commit_result
  - provider_usage_events: + contact_discovery_run_id, company_id
    (composite FKs).
  - commit_contact_candidate(workspace, candidate, contact, evidence):
    SECURITY INVOKER, idempotent per candidate, calls ingest_lead.
CHECKs:
  - revision needs profile; criteria needed; failed ⇒ code; final ⇒ time
  - normalized email lower-case/shaped; https profiles; bounded text
  - existing/duplicate/conflict ⇒ matched contact
  - conflict ⇒ never selected; selected ⇔ action; the action fits the match
  - committed ⇔ contact
Triggers:
  - run final states frozen
  - candidates only inserted while searching, changed while review, frozen
    once saved
  - an existing/duplicate match must be at the candidate's company
  - decided_by/at stamped; counts; updated_at; immutable keys
Indexes:
  runs        (company_id, created_at desc) · (workspace_id, created_at desc)
  candidates  UNIQUE (run, normalized_email) · (run, position) ·
              (matched_contact_id) WHERE NOT NULL
  usage       (contact_discovery_run_id)
Not added (no query uses them): (workspace_id, status) on runs,
(workspace_id, normalized_email) on candidates.
RLS: members select/insert/update; nothing for anon; no deletes;
column-level grants.

7. HUNTER DOMAIN SEARCH ADAPTER
--------------------------------------------------------------------------------
  - GET /v2/domain-search through the shared P1-E4 client: X-API-KEY header
    (never in the URL), 10 s timeout, one bounded retry for network/5xx/
    timeout only, same status mapping (400/401/403/429/451/5xx).
  - Error bodies are never read.
  - Params: domain, type=personal, limit ≤ 10, offset 0, job_titles (≤ 10,
    commas stripped), decision_maker=true only on request; seniority/
    department only from Hunter's lists.
  - An empty answer (200, no emails) or a 404 means "no results".
  - Mapping: §12. Not called: Email Verifier, Email Finder,
    Email/Combined Enrichment, Multi-Domain Search.

9. COMPANY / DOMAIN REQUIREMENT
--------------------------------------------------------------------------------
The server re-reads the company (active, this workspace), its stored
primary_domain and its company-level restriction.
  - No domain: "Add or enrich this company with a domain before finding
    contacts." The existing Enrich company action is shown alongside. The
    two credit operations are never chained.
  - Restricted: "This company is marked do not contact." No search; owners
    keep Lift restriction.
Both rules are checked on every action (start, retry, save).


--------------------------------------------------------------------------------
10. ICP ROLE INTEGRATION
--------------------------------------------------------------------------------
  - Default ICP preselected; any active profile selectable. The run stores
    icp_profile_id + icp_revision and the titles used.
  - Roles: ordered primary → secondary → fallback, then configured order;
    distinct titles; first 10 preselected; the user includes/excludes per
    search (unticked beyond 10 are disabled).
  - The ICP is never edited from the sheet.
  - No roles / no profile: typed titles (one per line, ≤ 10, this search
    only) + "Configure decision-maker roles in Settings to reuse them
    automatically."
  - No AI or invented titles. The server rebuilds the title list from role
    ids + typed titles; the browser's role text isn't trusted.


--------------------------------------------------------------------------------
11. SEARCH REQUEST MODEL
--------------------------------------------------------------------------------
Browser → {companyId, icpProfileId|null, roleIds[], manualTitles[],
decisionMakerOnly} (Zod, strict, UUIDs, ≤ 10 titles × 200 chars).
Server → company/ICP re-read → buildTargetTitles → run → one provider call
{stored domain, titles, decisionMakerOnly, limit 10}. A title search with no
results offers "Edit target roles" / "Search only Hunter-classified decision
makers" / try later, each an explicit new search (unit-tested: one request
per search).


--------------------------------------------------------------------------------
12. CONTACT CANDIDATES
--------------------------------------------------------------------------------
Stored per candidate:
  - name (first/last/full), title, email + normalized email
  - phone (shape-checked), https profile URL
  - Hunter seniority, department, decision-maker flag
  - verification status, confidence 0–100, source count + last-seen date
  - role match, match state, matched contact, decision/action, save result
Not stored: raw payload, source URLs/pages, twitter, organization/pattern,
generic inboxes. Results without a name or usable email are skipped and
counted ("1 result was not shown"). provider_external_id stays NULL
(Domain Search has no stable person id; none invented). Max 10 per search.


--------------------------------------------------------------------------------
13. ROLE MATCHING
--------------------------------------------------------------------------------
  - Normalize: NFKC, lower-case, punctuation → spaces, collapsed whitespace.
  - Whole-word containment ("Senior Operations Manager" ⊇ "operations
    manager"; "Operations Managerial" ⊉).
  - Highest priority wins.
  - Labels: Primary / Secondary / Fallback / Search title match;
    otherwise "No configured-title match"; plus "Hunter decision maker" and
    "Executive seniority". No numeric score.
Order:
  1 primary  2 secondary  3 fallback  4 typed-title
  5 Hunter-classified decision makers  6 others
  Within a group the provider's order is kept (confidence is shown, not
  used for sorting).


--------------------------------------------------------------------------------
14. VERIFICATION / CONFIDENCE
--------------------------------------------------------------------------------
  - Email status shown as Hunter reported it: Valid / Accept-all / Unknown /
    Invalid, or "Not provided" (any other value). Never upgraded.
  - No Email Verifier call.
  - Confidence: "Confidence N" (0–100, else —), text not colour, labelled
    "Hunter confidence".
  - The sheet states that both describe the email, not the role fit; they
    are never combined.


--------------------------------------------------------------------------------
15. DEDUPLICATION
--------------------------------------------------------------------------------
The P1-E1/P1-E2 contact rules (dedupe.matchContact + a workspace email
lookup), in order:
  1 email at this company → existing_contact
  2 email at another company → conflict
  3 same normalized name at this company → possible_duplicate
  4 otherwise new
Provider identity: none exists for Domain Search. Phone is never used
(unit-tested). No second algorithm.


--------------------------------------------------------------------------------
16. EXISTING-CONTACT HANDLING
--------------------------------------------------------------------------------
  - "Existing contact: <name>": Select → merge with the P1-E2 conservative
    contact merge (fill empty fields; differing values kept and reported as
    "Kept existing job title …"; never renamed), plus Hunter evidence.
  - Possible duplicate: explicit "Same person" (merge) or "Add as new"; never
    a silent merge. Browser-verified: Sam Ortiz merged, the empty email was
    filled, no second contact.

17. CROSS-COMPANY CONFLICTS
--------------------------------------------------------------------------------
"Contact already belongs to another company (<company>)". Dismiss only.
  - DB CHECK forbids selecting a conflict.
  - commit_contact_candidate refuses a new contact whose email exists
    anywhere in the workspace (23505) and only merges into the matched
    contact.
Verified (DB + browser read-back): the other company's contact was not
moved.

18. SUPPRESSION BEHAVIOUR
--------------------------------------------------------------------------------
  - Do-not-contact company: no search and no save (server-checked).
  - A restricted existing contact is labelled "Restricted" and stays
    restricted when enriched with evidence/empty fields (browser-verified).
  - Lift permissions are unchanged (owner/admin).
  - Nothing becomes "outreach-ready"; no outreach exists.


--------------------------------------------------------------------------------
19. CONTACT COMMIT
--------------------------------------------------------------------------------
"Save N contacts" processes selected, unsaved candidates in presentation
order, each through commit_contact_candidate → ingest_lead (one transaction
per person):
  - create: P1-E2 contact columns; the first new contact becomes primary
    only if the company has none
  - merge: P1-E2 merge patch
  - seniority: only Hunter "executive" maps to the Vleeds hint;
    junior/senior stay evidence
  - phone/profile: saved only when the person is selected, through the
    lead-core contact schema (an invalid phone is dropped)
Repeat saves are no-ops (DB-tested). The run completes when every selected
person is saved; a failure keeps it in review with a fixed note.

decision makers · estimated up to 1 credit" before the request and
"Estimated Hunter credits used" afterwards.
