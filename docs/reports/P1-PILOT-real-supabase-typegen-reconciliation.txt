4. WHY TYPEGEN INITIALLY BROKE TYPESCRIPT
--------------------------------------------------------------------------------
`npm run db:types` replaced the hand-maintained database.types.ts. Then
typecheck failed with 22 errors in 8 files. Three causes:

  a) The app imported a helper (MembershipRole) that only existed because
     the file was hand-written.
  b) `supabase gen types` cannot see SQL function nullability. PostgreSQL
     has no syntax to declare that a function argument or a RETURNS TABLE
     column is nullable, so the generator emits all of them as non-null.
     Optional arguments (those with DEFAULT) become `p_x?: T`, not
     `p_x?: T | null`. The hand-written file had encoded `| null`, and the
     DAL passed `null` explicitly.
  c) NOT NULL jsonb columns are generated as `NonNullable<Json>`. The DAL
     widened plain arrays to `Json` with `as Json`, and that includes null.

None of these is a database defect. The 219 real-Postgres tests prove the
SQL behaviour, and no migration needed to change.

5. HAND-MAINTAINED CONSTRUCTS DISCOVERED
--------------------------------------------------------------------------------
Method: both files were resolved with the TypeScript checker and every
Tables.*.{Row,Insert,Update}, Functions.*.{Args,Returns} and Enums member
was listed and diffed. The generated schema is treated as authoritative.

  1. Application helper aliases
     - MembershipRole ("owner" | "admin" | "member"), exported from the
       generated file and used by Enums.membership_role and memberships.role.
  2. Stale/mistyped generated schema
     - None. Every table/column the old file declared exists in the
       generated one with the same base type.
  3. RPC argument assumptions (old `| null`, generated non-null)
     - ingest_lead: p_import_row_id, p_enrichment_run_id
     - list_companies: p_qualification, p_grade, p_restricted,
       p_has_contact, p_country
     - record_contact_attempt: p_note, p_source_task_id, p_next_kind,
       p_next_due_at, p_next_note, p_suppression_scope, p_suppression_reason
     - schedule_follow_up: p_note
     - save_lead_score_trusted: p_score, p_grade (REQUIRED args; see §9)
     All except save_lead_score_trusted are `DEFAULT NULL` in SQL.
  4. Table Row/Insert/Update assumptions
     - The old file listed only the Insert/Update columns the app wrote,
       and used `never` for tables written only through functions
       (contact_attempts, follow_up_tasks, lead_scores, organizations
       Insert, lead_sources Update). The generated file lists every column.
       That is a strict superset, so no app change was needed. Table GRANTs and
       RLS remain the real write boundary (verified by the DB suite).
  5. Enum assumptions
     - membership_role is the only PostgreSQL enum. Its values are identical.
       Other state columns are text + CHECK and are `string` in both files.
  6. Nullable/non-null differences
     - jsonb NOT NULL columns (workspaces.settings, import_batches.headers,
       import_rows.raw_data, contact_discovery_runs.selected_titles):
       old `Json`, generated `NonNullable<Json>`. The generated type is
       more accurate.
  7. Function-result assumptions (old nullable, generated non-null)
     - list_companies: primary_domain, location, grade, score,
       coverage_percent
     - today_ready_candidates: location, coverage_percent, last_attempt
     - today_due_tasks: note, job_title, phone
     These did NOT cause compile errors, because the generated types are
     narrower. But they are wrong: they can be NULL at runtime (each was checked against
     the function body and its LEFT JOINs/nullable columns). They are now
     re-widened outside the generated file (§6).

7. DAL RECONCILIATION
--------------------------------------------------------------------------------
No `any`, `@ts-ignore`, `@ts-expect-error` or new casts were added. Three
`as Json` casts were removed.

  workspaces.ts         MembershipRole now imported from app-types.
  companies.ts          list_companies filters: `?? undefined` (omit when
                        unset). Rows annotated ListCompaniesRow[]. Annotating
                        is a widening assignment, not a cast. ingest_lead: no
                        contact → omitted. p_import_row_id: null removed.
  contacts.ts           ingest_lead: p_import_row_id: null removed.
  enrichment.ts         ingest_lead: p_contact: null and p_import_row_id: null
                        removed.
  contact-workflow.ts   record_contact_attempt / schedule_follow_up optional
                        args: `?? undefined` / optional chaining.
  contact-discovery.ts  selected_titles: TargetTitle[] passed directly (it
                        is JSON-compatible; the `as Json` cast was the only
                        source of the null).
  imports.ts            headers / raw_data: string[] passed directly.
  today.ts              RPC results annotated TodayReadyCandidateRow[] /
                        TodayDueTaskRow[].

Why omitting matches sending null: every affected optional argument is
declared `DEFAULT NULL` (verified in the migrations). supabase-js sends RPC
args as a JSON body, where undefined keys are dropped. PostgREST then
applies the SQL default, which is NULL. Each of these functions has exactly
one overload, so omitting keys cannot select a different function. The
UI-review mock treats missing and null alike (`== null`, `??`,
truthiness).

9. TRUSTED SCORE WRITER NULLABLE-RESULT HANDLING
--------------------------------------------------------------------------------
save_lead_score_trusted takes p_score integer and p_grade text with no
default. An EXCLUDED result is persisted with score NULL, grade NULL and
exclusion reasons. The function and the lead_scores CHECKs enforce that
pairing, and the P1-E7 DB tests (now on real Postgres) cover it. The
generator reports both as `number` / `string`.

Semantics are unchanged: there is no fake numeric score and no fake C grade.

Boundary: src/lib/supabase/trusted-score-writer.ts types its PRIVATE
service-role client with `TrustedScoreDatabase`. That type is the generated
`Database` with one change: save_lead_score_trusted.Args has p_score and
p_grade widened via WithNullable. It is built with Omit/intersection from
the generated types, not cast, so:
  - every other arg, the return type, and every other table/function stay
    exactly as generated
  - the client is never exported; the rest of the app keeps the plain
    generated `Database`
  - a probe confirmed the client still rejects missing args and wrong arg
    types, and that the return type remains `string`
The comment in the module explains why the boundary exists.
