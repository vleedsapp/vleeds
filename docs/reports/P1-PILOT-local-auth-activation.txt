--------------------------------------------------------------------------------
1. ROOT CAUSE
--------------------------------------------------------------------------------
supabase/config.toml has two keys named `enable_signup` that do different
things. The running Auth container's environment showed the mapping (CLI
2.120.0):

  [auth]       enable_signup = false  ->  GOTRUE_DISABLE_SIGNUP=true
  [auth.email] enable_signup = false  ->  GOTRUE_EXTERNAL_EMAIL_ENABLED=false

The second key, despite its comment ("Allow/disallow new user signups via
email"), turns off the email provider entirely. So EVERY password sign-in
was rejected: 422 email_provider_disabled, "Email logins are disabled".
That included the seeded users and any admin-created user. The app
reported the 422 as "Sign-in is unavailable right now". Both keys were
set to false in P0-E1-S1, intended as "invitation only". Before Docker
was available, only the UI-review mock had exercised sign-in, so the
problem never surfaced.

The earlier "Password should be at least 12 characters" error was not a
bug. It is the intended policy (`minimum_password_length = 12`), which
was not changed.

--------------------------------------------------------------------------------
3. WHY PUBLIC SIGNUP REMAINS DISABLED
--------------------------------------------------------------------------------
"Provider enabled" (users with a password can sign in) is separate from
"signup allowed" (anyone can create an account). Signup is controlled by
GOTRUE_DISABLE_SIGNUP=true, which comes from [auth] enable_signup = false
and was not touched.

Verified: POST /auth/v1/signup with the publishable key returned
  {"code":422,"error_code":"signup_disabled","msg":"Signups not allowed for this instance"}
and no auth.users row was created. The app has no signup UI or
supabase.auth.signUp call (src/ only calls signInWithPassword). Accounts
are still created only by an admin (Admin API / Studio / seed).

4. TEST-USER CREATION METHOD
--------------------------------------------------------------------------------
New script: scripts/dev/create-local-test-user.mjs
  node --env-file=.env.local scripts/dev/create-local-test-user.mjs

  - Uses the supported Auth Admin API (supabase-js auth.admin: listUsers,
    createUser / updateUserById). No SQL into auth.users/auth.identities.
  - Refuses to run unless NEXT_PUBLIC_SUPABASE_URL is http:// on a loopback
    host (127.0.0.1, localhost, ::1). It also refuses NODE_ENV/VERCEL_ENV
    production. Verified: https://<ref>.supabase.co and http://10.0.0.5:54321
    are refused with exit 1.
  - Idempotent. A second run found the user (same id), re-synced the
    password from .env.local and kept the email confirmed.
  - Creates the user with email_confirm: true.
  - Prints only the email and user id, never keys, passwords or tokens.
  - Reads credentials only from the environment (.env.local).

.env.local (git-ignored) received:
  SUPABASE_SERVICE_ROLE_KEY   the LOCAL stack's key (from `supabase status`).
                              It also enables the P1-E7 trusted score writer
                              locally.
  VLEEDS_LOCAL_TEST_EMAIL     pilot@vleeds.test (.test is accepted by Auth)
  VLEEDS_LOCAL_TEST_PASSWORD  24 random alphanumeric characters
.env.example lists the two VLEEDS_LOCAL_TEST_* names with empty values.
