4. MIGRATION / SCHEMA (20261009000000_lead_core_foundation.sql)
--------------------------------------------------------------------------------
Five tables, each with workspace_id → workspaces ON DELETE CASCADE, RLS
enabled, column-level grants, nothing for anon, no DELETE grant, updated_at
triggers where rows change, and prevent_tenant_key_change triggers on every
ownership/relationship key. Children reference parents through composite
FKs (workspace_id, parent_id); contacts also declare
unique (workspace_id, company_id, id), so evidence and suppression can require
"this contact AT this company". No new functions: policies reuse
private.is_workspace_member and private.has_workspace_role.
Indexes (each tied to a query or FK):
  companies   (workspace_id, archived_at) · (workspace_id, qualification_state)
              WHERE active · (workspace_id, normalized_name) [matching] ·
              UNIQUE (workspace_id, primary_domain) WHERE domain AND active
  contacts    (workspace_id, company_id) · (workspace_id, normalized_email)
              WHERE email · UNIQUE (company_id) WHERE is_primary AND active
  lead_sources (workspace_id, company_id) · (workspace_id, contact_id) ·
              UNIQUE (workspace_id, provider_key, external_record_id,
              field_key, company_id, contact_id) NULLS NOT DISTINCT
              WHERE external_record_id
  lead_scores (workspace_id, company_id) · (icp_profile_id, icp_revision) ·
              UNIQUE (company_id, icp_profile_id, icp_revision)
  suppression_records (workspace_id, company_id) · (workspace_id, company_id,
              contact_id) WHERE contact · UNIQUE active target NULLS NOT DISTINCT
Policies
  companies, contacts   SELECT/INSERT/UPDATE  is_workspace_member
  lead_sources          SELECT/INSERT         is_workspace_member (append-only)
  lead_scores           SELECT                is_workspace_member (no API writes)
  suppression_records   SELECT/INSERT         is_workspace_member
                        UPDATE                has_workspace_role(owner, admin)

5. COMPANIES
--------------------------------------------------------------------------------
canonical_name (display, 1–200), normalized_name (matching), website_url
(http/https), primary_domain (normalized host), primary_phone (as entered,
3–40) + primary_phone_normalized (+digits or null), location jsonb ≤2 KB
{countryCode, region, city, postalCode, addressLine1, addressLine2} (all
optional, any country), employee_count_min/max (whole, ≥0, min ≤ max),
qualification_state, qualification_reason ≤500, notes ≤5000, archived_at,
created_by, timestamps. No provider-speculative fields.
Deviation: the normalized columns are computed in TypeScript
(src/lib/lead-core/normalize.ts) rather than generated in SQL. That keeps one
implementation shared with future ingestion. The DB CHECKs their format
(lower-case hostname, +E.164-like phone, trimmed non-empty name).


--------------------------------------------------------------------------------
6. CONTACTS
--------------------------------------------------------------------------------
company_id (same-workspace FK), first/last/full name (full required), job
title, seniority (reuses the ICP hints: executive|director|manager|
individual_contributor), email + normalized_email (pair CHECK, lower-case),
phone + phone_normalized, linkedin_url (https), is_primary (one active
primary per company; an archived contact can't be primary), status
(active|left_company|unknown), notes, archived_at. Name + title + company are
enough. company_id and workspace_id are immutable, so a contact can't be moved.
Email is indexed but not unique (shared inboxes); ingestion decides.


--------------------------------------------------------------------------------
7. LEAD / SOURCE EVIDENCE (lead_sources)
--------------------------------------------------------------------------------
Subject: company_id and/or contact_id (at least one; if both, the contact must
belong to that company). source_kind manual|csv|public_dataset|website|api|
other (no provider names). provider_key free text ^[a-z0-9][a-z0-9_.-]{0,63}$.
external_record_id requires provider_key. field_key
^(company|contact)\.[a-z][a-z0-9_]*$, with documented keys (company.name,
.website, .domain, .phone, .location, .employee_range; contact.name, .title,
.email, .phone, .linkedin) used for labels. observed_value jsonb ≤2 KB (no
payloads). confidence 0–100 (data confidence, not fit). observed_at,
source_url. Append-only: insert grant only, keys immutable. External identity
is unique per workspace + provider + record + field + subject, so the same
record can exist in another workspace.


--------------------------------------------------------------------------------
8. QUALIFICATION STATE
--------------------------------------------------------------------------------
unreviewed (default) | needs_review | qualified | unqualified, plus an
optional reason (≤500). It is an operational workspace decision, independent
of any ICP and of scores. Archival stays separate (archived_at). Implemented
as a mutation: the drawer's control calls setCompanyQualification (server
action), which authenticates, re-authorizes the workspace, validates with Zod
and writes only those two columns through the DAL. RLS allows any workspace
member. The page refreshes in place.


--------------------------------------------------------------------------------
9. SCORE STORAGE (lead_scores)
--------------------------------------------------------------------------------
company_id + icp_profile_id + icp_revision (both FKs within the workspace),
score 0–100, grade A|B|C, breakdown (object ≤4 KB; documented keys
company_fit, geography_fit, decision_maker_fit, buying_signal_fit,
exclusion_penalty), status pending|scored|stale, scored_at. Rules:
  - scored needs score, grade and scored_at
  - pending has no score or grade
  - one row per company × profile × revision
  - the DB never derives a grade; grades will come from the saved ICP thresholds
Read-only for API roles; the future scoring engine writes. Display rule: a
result is current only if scored at the profile's current revision. Older
revisions show "Outdated: profile changed". No automatic stale propagation:
when scoring arrives, a revision change should mark that profile's scored
rows stale and queue re-scoring (documented). Nothing computes scores in this
story.

10. DEDUPLICATION MODEL
--------------------------------------------------------------------------------
Normalization (normalize.ts)
  domain   scheme, www., path, query, port, credentials and trailing dot are
           dropped; IDN → punycode; invalid hosts, IPs and numeric TLDs → null.
           "https://www.example.com/", "http://example.com/", "example.com"
           → example.com
  name     NFKC, lower-case, whitespace collapse; drops . , quotes/apostrophes;
           "&" ≡ "and"; dash variants. Legal/meaningful words (LLC, Ltd, Inc,
           Group, Holdings) are KEPT.
  email    trim + lower-case only (plus-tags and dots kept)
  phone    comparison value only for international input ("+…"/"00…"),
           extensions dropped; national numbers → null (country unknown).
           LIMITATION: no phone library; the display value is always kept.
Matching (dedupe.ts), within one workspace only
  company  1 provider identity → match · 2 domain → match · 3 international
           phone → review · 4 normalized name + same country and city/region
           → review · else new. Similar names never auto-merge.
  contact  1 email → match · 2 provider identity → match · 3 same name at the
           same company → review · else new. Phone is NEVER used.
Database backstops: one active company per domain per workspace (archived
rows don't block); provider-record uniqueness on evidence.


--------------------------------------------------------------------------------
11. SUPPRESSION RECORDS
--------------------------------------------------------------------------------
company_id (required), contact_id (contact scope only), scope company|contact,
reason ≤500, active. company scope ⇒ no contact; contact scope ⇒ a contact
that belongs to that company in that workspace. One active record per target.
Members add; owners/admins lift or edit; target and scope are immutable.
Shown as "Restricted" on rows and "Company restricted" / "Contact restricted"
/ "Do not contact this company" in the drawer. NOT enforced anywhere yet,
because no contact actions exist. Every future call, email or campaign action
must check active records (documented in the product and data-model docs).


--------------------------------------------------------------------------------
12. DAL IMPLEMENTATION
--------------------------------------------------------------------------------
src/lib/dal/ split by domain. Everything is server-only, uses the user-scoped
client (RLS) and narrows results to DTOs (src/lib/lead-core/views.ts).
  listCompanies(ws)          ≤100 active companies, newest activity first, with
                             primary contact, contact count, evidence count,
                             company restriction, current default-profile grade
  getCompanyDetail(ws, id)   null for unknown/archived/foreign/malformed ids
                             (indistinguishable); last 25 evidence + total
  setCompanyQualification    two columns, typed failure, zero rows → forbidden
  helpers                    contactsForCompanies, evidenceFor (company + contact
                             evidence, de-duplicated), scoresForCompanies
                             (+ profile names/revisions), activeSuppressions
Stored jsonb (location) is re-parsed with Zod; invalid → treated as absent.
Every query filters by workspace_id in addition to RLS.

19. CODE-QUALITY FINDINGS
--------------------------------------------------------------------------------
Verified
  Q1  Workspace ownership: every row has an immutable workspace_id; all child
      links are composite FKs, so even a member of two workspaces cannot
      cross-link them (tested).
  Q2  Relationship integrity: contacts can't change company; evidence and
      contact restrictions require the contact to belong to the named
      company; scores require company and profile in the same workspace.
  Q3  Input validation: Zod on the mutation (qualification) and for all future
      inputs; DB CHECKs on formats, sizes, enums and ranges.
  Q4  User-supplied ids: workspaceId and companyId are UUID-checked,
      re-authorized (findWorkspace) and filtered by workspace_id + RLS. Foreign,
      unknown and malformed company ids behave identically (no drawer).
  Q5  Errors: DB failures are mapped to fixed messages; reads throw
      DataAccessError to the generic error boundary.
  Q6  Client/server boundary: no browser DB client; Client Components receive
      DTOs only; actions accept no redirect targets; bundle scan clean.
  Q7  Least privilege: scores are not API-writable; evidence is append-only;
      lifting restrictions is owner/admin; nothing is deletable.
Findings / follow-ups
  F1 (Low)  Normalized columns are app-computed. A direct API writer (an
            authenticated workspace member) could store a normalized_name that
            doesn't match canonical_name. Formats are DB-checked; P1-E2 writes
            only through the DAL helpers. Consider a DB-side recompute if
            direct API writes are ever allowed.
  F2 (Low)  Members can archive companies and edit any company/contact field
            (collaborative model, as specified). Revisit if role-based
            ownership is needed.
  F3 (Low)  RLS uses is_workspace_member per row; add my_workspace_ids()
            (data-model §2) before lists grow large.
  F4 (Info) Lead list is capped at 100 with no pagination yet (stated in the UI).
  F5 (Info) Carried: no CSP; forbidden pages return HTTP 200.
