1. SUMMARY
--------------------------------------------------------------------------------
Vleeds is now usable for daily selling. Today answers "what should I do now?"
from real data:
  - callbacks due and follow-ups due, labelled Overdue / Due now / Later today
  - companies ready to contact: current A/B grade for the default ICP, each
    with one recommended contact
  - the attempts recorded today
  - a compact Needs attention area

The seller calls from their own phone and records the outcome in Vleeds:
  - "Call" / "Start contact" opens a focused sheet with Copy number and Call
    on device (a tel: link).
  - Nothing is recorded until an outcome is submitted.
  - Each outcome is one database transaction: the attempt, completion of the
    source task, the next task, and (for Do not contact only) the
    restriction.
  - Each contact has at most one open next action. Tasks can be scheduled,
    rescheduled, completed without a call, or cancelled.
  - The company drawer gains per-contact next actions and an Activity
    timeline.
  - Workspace time zone (IANA, default UTC) defines "today".

The P1-E6 medium follow-up is closed. Scores can no longer be persisted by
the authenticated API role: a server-only trusted writer (the only use of
SUPABASE_SERVICE_ROLE_KEY) calls save_lead_score_trusted, which still
checks the acting member, revision, fingerprint and thresholds.

A small explicit batch, "Refresh lead scores" (≤ 50 unscored/outdated
companies), uses the same evaluator and writer.

No calling provider, email, SMS, campaigns, automated follow-up, AI scoring
or background jobs.

Quality gate: npm.cmd run verify EXIT 0 (see §25). Browser review P1-E7:
72/72; all earlier reviews pass (§25).

5. P1-E6 SCORE-WRITE HARDENING
--------------------------------------------------------------------------------
Choice: SUPABASE_SERVICE_ROLE_KEY in ONE server-only module. The repository
had no other privileged mechanism, and supabase-js with the service key
is the established Supabase pattern. The change is isolated to score
persistence; there is no privileged DAL.
  - save_lead_score_trusted(p_actor_user_id, …)
      · EXECUTE granted to service_role only; revoked from authenticated
        and anon
      · it still verifies that:
          - the actor is a member of a non-archived workspace
          - the company and profile belong to the workspace
          - the ICP revision is current
          - the fingerprint equals scoring_input() now
          - score and coverage are in range
          - the grade follows the thresholds
          - an exclusion has ≥ 1 named reason and no score/grade
      · it records scored_by
  - src/lib/supabase/trusted-score-writer.ts
      · import "server-only"
      · its client is private (never exported); one .rpc call, no .from()
      · the key is read from server env only and never logged (errors log
        the code only)
      · a sb_publishable_ key is refused
  - Flow: the server action authenticates the user, re-reads the canonical
    input, runs the pure evaluator, then calls persistLeadScore(session
    user id, …). The browser still sends only ids/choices (strict schemas,
    tested).
  - Without the key, Evaluate fit / Refresh say "the trusted score writer
    isn't configured". There is no fallback path.
  - Guards:
      · unit tests: the module is the only reader of the key name; only
        dal/scoring.ts and today/actions.ts import it; no "use client" file
        references it
      · the bundle check fails on the key name, the function name or the
        writer
DB tests:
  - authenticated/anon can't execute it; service_role can; the old RPC is
    gone
  - a member's direct call with fabricated values → 42501
  - non-member / outsider / null actor / foreign workspace or company →
    42501
  - stale fingerprint or revision → 55000
  - inconsistent grade, bounds, an exclusion without reasons or with a
    score → 23514
  - direct inserts/updates of lead_scores → 42501
Browser: a user-session call to the trusted writer is refused (mock
mirrors the grant); Evaluate fit and Refresh work through the writer.

6. WORKSPACE TIMEZONE
--------------------------------------------------------------------------------
Stored as an IANA name (default UTC; existing workspaces get UTC).
  - Edited in Settings → Business profile → Time zone (owners/admins).
    Members read it in the Business profile card.
  - The choice list comes from the runtime (Intl.supportedValuesOf); there
    is no hand-maintained list. The saved zone is kept even if a browser
    doesn't list it.
  - Validated server-side (runtime list) and in the database (shape +
    pg_timezone_names).
  - The browser zone is never stored.
  - Timestamps stay timestamptz/UTC.
  - The zone is used only for: today bounds, display ("Today · 10:42"),
    reading typed date/time, and overdue/due-today classification.
  - Conversions use @date-fns/tz (TZDate) and date-fns; no manual offset
    arithmetic.
  - DST: 23/25-hour days are handled. A non-existent local time moves
    forward by the gap; this is documented and tested.

7. CONTACT ATTEMPTS
--------------------------------------------------------------------------------
Append-only history (P1-E7 channel = phone).
  - Created only by record_contact_attempt, with server now() as
    attempted_at and created_by = the caller.
  - No API insert/update/delete; an update trigger blocks edits even for
    the trusted role.
  - Opening a sheet, copying a number or a tel: link creates nothing
    (browser-verified).
  - Resubmitting the same form returns the same attempt (request_id).


--------------------------------------------------------------------------------
8. DISPOSITIONS
--------------------------------------------------------------------------------
Product labels:
  No answer · Left voicemail · Connected — interested ·
  Connected — not interested · Callback requested · Follow-up needed ·
  Wrong number · Do not contact · Other
Rules (pure module, enforced again in SQL):
  - Callback/Follow-up: due date + time REQUIRED (callback / follow_up
    task)
  - No answer / Voicemail: optional retry_call
  - Interested: optional follow-up
  - Not interested / Wrong number: no next action in this step
  - Other: note required; optional next action
  - Do not contact: scope required (This person / Entire company)
  - Due times must be in the future (≤ 5 years)
Ready afterwards (no task):
  - Not interested / Wrong number: not returned automatically
  - Others: excluded for the rest of the workspace day only
Nothing changes qualification, grade, fit or coverage.


--------------------------------------------------------------------------------
9. FOLLOW-UP TASKS
--------------------------------------------------------------------------------
  - One open task per contact (partial unique index). Schedule refuses a
    second one (VL004); the drawer offers Reschedule instead.
  - Reschedule changes due_at only (id, creator and created_at kept;
    verified).
  - Complete = handled without a call; no attempt is created (verified).
  - Cancel keeps the history.
  - Overdue / Due now / Later today / Blocked are derived, never stored.
  - The source attempt must be the same contact's (FK).


--------------------------------------------------------------------------------
10. TRANSACTIONAL ATTEMPT WORKFLOW
--------------------------------------------------------------------------------
record_contact_attempt, in one transaction:
  1. checks membership
  2. replays a known request_id
  3. locks the contact row
  4. checks the relationship and the blocker (restricted / left / no
     phone / archived)
  5. checks the outcome rules
  6. checks the source task (open, same contact)
  7. inserts the attempt
  8. completes the source task
  9. replaces any other open task with the next task
 10. for DNC: inserts the restriction and cancels in-scope tasks
The browser can't supply relationships, actor or timestamps (strict
schemas; the DB re-reads everything). Browser-verified: an overdue
callback was logged as "Callback requested". The source task completed,
a new callback task was created, and the overdue item left Today.


--------------------------------------------------------------------------------
11. DO-NOT-CONTACT BEHAVIOUR
--------------------------------------------------------------------------------
Requires an explicit scope; an optional reason.
  - This person: a contact restriction; that contact's open task is
    cancelled; other contacts are untouched.
  - Entire company: a company restriction; every open task at the company
    is cancelled.
  - Reuses suppression_records (any member adds; only owners/admins lift).
  - Afterwards: no new attempts or tasks (VL001); drawer actions are
    removed; Today shows remaining tasks as blocked.
Allowed on a contactable record because it creates the restriction (also
for a contact without a phone). Not allowed on an already-restricted
target.

13. READY-TO-CONTACT ELIGIBILITY
--------------------------------------------------------------------------------
Company (default ICP):
  - active
  - CURRENT result (revision + fingerprint, the same rule as Leads)
  - grade A or B (never C, Excluded, Outdated or Not scored)
  - qualification unreviewed or qualified
  - no company restriction
Contact:
  - not left the company; usable phone (≥ 3 digits); not restricted
  - no open task: a future task waits; a due task is listed as due work
  - latest outcome rule (§8)
Order: A before B, fit desc, name, id. Coverage never reorders fit.
The SQL returns current A/B facts; the pure module decides eligibility
(single source of the business rules).


--------------------------------------------------------------------------------
14. RECOMMENDED CONTACT
--------------------------------------------------------------------------------
One per company, from ELIGIBLE contacts. The first match decides:
  1. default-ICP primary role
  2. secondary role
  3. fallback role (bestRoleFor: the same whole-word matching as P1-E5/E6)
  4. contact marked primary
  5. name, then id
If the best person is restricted, has a task or no phone, the next
eligible one is used (browser: Willow → Lou Brandt; Harbor → Robin over
primary contact Casey, who had a task).


--------------------------------------------------------------------------------
15. DUE WORK AND BLOCKED TASKS
--------------------------------------------------------------------------------
Open tasks with due_at < end of the workspace day.
  - Overdue (before today's start) · Due now (≤ now) · Later today
  - Order: overdue first, then due_at, then id
  - Callbacks tab = callback; Follow-ups tab = follow_up + retry_call
  - Cards show: time, state label, kind, company, contact, title, tappable
    phone, short note, and Call / Reschedule / Complete / Cancel task
Blocked (company/contact restricted, contact left, no phone, archived):
  - never deleted and not counted
  - shown under Needs attention with the reason and Cancel task
