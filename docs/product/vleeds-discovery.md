# Vleeds — Discover (company discovery)

Status: implemented in P1-E3, extended in P1-E4 (enrichment hand-off) · Code: `src/lib/providers/company-discovery/*`, `src/lib/discovery/*`, `src/lib/dal/{discovery,provider-usage}.ts`, `src/app/w/[workspaceId]/discover/*`, `src/components/discover/*` · Migration: `20261011000000_company_discovery_foundation.sql` · Provider details: `docs/providers/google-places.md`

## 1. What Discover does

Discover helps a workspace **find companies that may fit its target market**, using an external discovery provider. The first one is Google Places. It is interactive:

```
ICP (optional guide) → Discovery run (one search) → Provider → Candidate references → Review (select / dismiss)
```

- A search runs only when the user presses **Find companies**. Nothing runs on page load, on a schedule or in the background: no sweeps, no polling.
- One provider page per action. **Load more** fetches the next page.
- Results are **candidates**. They are not companies in Leads. Discover never adds companies to Leads by itself.
- No scoring is done: candidates have no grades.

## 2. The screen

1. **Find companies** (ready to search)
   - **Ideal customer profile:** the workspace's default profile is preselected.
   - **What are you looking for?** Free text. It is prefilled from the profile's first industry/category, and the profile's industries and keywords appear as one-click suggestions. The user can always type their own words. Nothing is generated by AI.
   - **Where:** the profile's target geographies first, then **Another location…** (country plus optional region and city), or **No specific location**.
   - **Results per page:** 5, 10 or 20, within the provider's limit.
2. **Results** (the open search). On desktop this is a table: Company, Location, Category, Vleeds status, Decision. On phones it shows cards.
   - Above the results: the search, with a usage summary ("This search: Google Places · 2 requests · 7 candidates"; "This month: N requests").
   - Below them: the provider attribution ("Google Maps", plus any third-party providers) and **About these results** (how the provider ranks results).
   - Actions: **Load more**, **Done reviewing**, **Cancel search**.
3. **Recent discovery activity:** the last 10 searches. Each shows the query, where, provider, date, the number of references, the number selected and the status (In review, Completed, Cancelled, Failed). Failed searches can be **retried**. Monthly usage is shown here too.

Without a configured provider, the screen loads normally and says **"Company discovery is not configured yet."** Recent activity still shows.

## 3. How the ICP and geography are used

- The ICP only **guides** the search. Its industries/categories and keywords become suggestions, and its target geographies become the **Where** options. The run records the profile id and revision it was started from.
- Geography stays **structured** (`countryCode`, `region`, `city`, `label`) all the way to the provider adapter. The Google adapter turns it into text ("bookkeeping services in Toronto, Ontario, Canada") and passes the country as `regionCode`. A future location-aware provider can use the structure directly. There is no geocoding dependency.
- No industry, place or wording is built into the code. Everything comes from the workspace's configuration or the user.

## 4. Candidate status: what Vleeds can truthfully say

Status uses **durable data only**. Provider names and addresses are never compared or stored, so there is no hidden name/address database.

| Status | Meaning |
| --- | --- |
| **Existing company** | The provider id is linked to an active company of this workspace through durable source evidence (`lead_sources` with the same `provider_key` and `external_record_id`). The row links to the company. |
| **Seen before** | An earlier search in this workspace found the same provider id. |
| **New reference** | Neither. |

For Google, **`google_places` + Place ID** is the identity. Future providers whose data may be kept will also match on domain, email and company identity through the existing P1-E1/P1-E2 rules.

## 5. Decisions

| Action | Result |
| --- | --- |
| **Select** on a new or seen-before reference | `needs_enrichment`: Vleeds keeps the reference until company data is found (P1-E4: **Find company data**) |
| **Select** on an existing company | `selected`: it **is** that company; no duplicate is created |
| **Dismiss** | `dismissed` |
| **Undo** | back to `unreviewed` |

**Done reviewing** completes the run and keeps its decisions. **Cancel search** cancels it. Completed and cancelled runs are final (enforced by the database).

## 6. Provider architecture

Every provider implements one interface (`CompanyDiscoveryProvider` in `types.ts`):

- `providerKey`, `label`, `attribution`
- `isConfigured()`
- `getCapabilities()`
- `searchCompanies(input)`: structured query, geography, page size and an optional opaque cursor
- `normalizeCandidate(result)`

The server-only registry (`registry.ts`) returns providers by key. Pages, actions and the DAL never see a provider's request or response shapes.

**Capabilities** make the differences between providers explicit:

| Capability | Google Places |
| --- | --- |
| `companyDiscovery` | yes |
| `durableExternalId` | yes (Place ID) |
| `durableCompanyFields` | **no** |
| `supportsPagination` | yes (cursor) |
| `supportsTextQuery` | yes |
| `supportsGeographyText` | yes |
| `maxPageSize` | 20 |
| `fieldRetention` | externalId durable; name, address and category transient |

## 7. Why Google content is not stored as lead data

Providers license their data differently. Google Maps Platform lets apps keep **place IDs** indefinitely but restricts storing other Places content. Vleeds therefore:

- stores only the Place ID, its own match state and the user's decision for each candidate. There are no name, address, phone, website, rating or review columns, and no raw payloads.
- keeps names, addresses and categories only in the open search: in server memory while answering and in the browser's state afterwards. Reloading the page drops them, so history shows queries and counts.
- never turns Google content into company records. A selected reference waits as `needs_enrichment`.

## 8. Relationship to ingestion (P1-E2) and future providers

The ingestion pipeline stays **one** pipeline:

```
normalize → classify (dedupe) → review (create / merge / skip) → ingest_lead → evidence
```

- **Google Places (P1-E3)** stops **before** this pipeline: it has no durable company fields (`durableCompanyFields: false`). It produces only references.
- **A future durable-data provider** (one whose licence permits storing company name, website/domain, phone and metadata) returns those fields marked durable. Its selected candidates are then normalized with `src/lib/lead-core`, classified with `dedupe.ts`, reviewed with the same create/merge/skip decisions, and written with `ingest_lead` and provider-keyed evidence.
- The **enrichment step** for `needs_enrichment` references uses the same path. Its evidence links the provider id to the company, which is what makes **Existing company** work in later searches.

None of this needs changes to `discovery_runs`, `discovery_candidates`, `provider_usage_events` or the review UI.

## 8a. Enrichment hand-off (P1-E4)

Product details: `vleeds-company-enrichment.md`.

- A result *saved for enrichment* offers **Find company data** while the search is open (only when an enrichment provider is configured; otherwise the Company data panel says "Company enrichment is not configured yet.").
- The result's **transient** name is sent to the server only as input to the free domain lookup. It is never written to the run, the result, evidence or logs (a CHECK on `company_enrichment_runs` forbids a stored name for discovery references).
- After a create or merge, `ingest_lead` links the **Place ID** to the committed company (`lead_sources`, identity only, no content) and marks the reference `selected` / `existing_company`. This is allowed even after the search was completed; nothing else about a finished search can change. Later searches therefore show the place as **Existing company**.
- References selected in earlier searches are listed under **Company data → Saved for enrichment** without names (they were transient): the user enters the name or domain.
- Discover also has a standalone **Enrich a company** (name or domain), and the monthly enrichment usage with **estimated** credits.

## 9. Who can do what

Any member of a workspace can search, decide and cancel, and can see the workspace's runs and usage; this is the collaborative model. There are no new roles, and Settings/ICP permissions are unchanged. Provider configuration is server-side (environment) for now. Settings shows no provider controls, and *Enrichment providers* stays inactive: Google Places is a discovery source, and the enrichment provider (P1-E4, Hunter) is configured in the server environment too.

## 10. Limitations and next steps

- One provider (Google Places), text search only. Google returns at most 60 results per query.
- There is no automatic retention for run history. It holds only Vleeds data: query, geography, counts and decisions.
- There are no cost estimates. Usage counts are shown instead, because Google pricing isn't snapshotted.
